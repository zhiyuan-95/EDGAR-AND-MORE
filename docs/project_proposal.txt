## Executive Summary

Extend the existing SEC/Arelle reporting application into a local, analyst-facing financial metric explorer. A background pipeline will acquire and normalize Inline XBRL filings, preserve their evidence in SQLite and retained files, resolve seven conventional metrics, and publish immutable verified result versions. A local API and browser frontend will read those publications without running Arelle during web requests.

The first release will show five annual periods and the latest twelve filed 10-Q periods for:

1. Revenue
2. Operating Income
3. Net Income
4. Total Assets
5. Total Liabilities
6. Equity
7. Operating Cash Flow

The main product experience is deliberately simple: choose a company and metric, see its trend, click any point to inspect why it exists, and download the metric together with its supporting evidence. The database is local and canonical; JSON, CSV, and ZIP are generated exports rather than the source of truth.

## Problem Statement

The current application already discovers SEC filings, processes Inline XBRL with Arelle, and produces evidence-rich annual and quarterly TXT reports. Those reports are valuable for project-owner inspection, but they do not provide a durable query model or a simple interface for analysts.

An analyst needs two experiences at once:

- a fast view of conventional financial trends; and
- an auditable path from every displayed value back to the exact filing facts, contexts, mappings, derivations, and validation evidence that produced it.

Running SEC acquisition and Arelle extraction inside a web request would be slow, failure-prone, and difficult to audit. Discarding the processed evidence after metric generation would make the result impossible to verify or download. The system therefore needs durable local storage and a clean boundary between processing and serving.

## What Makes This Cool

The product is a "chart-point-to-proof" explorer. Each point on a familiar financial trend is treated as an inspectable claim rather than an unexplained number. A user can see whether the point was directly reported, deterministically derived, unresolved, conflicting, or invalid, then download the exact evidence behind that state.

The LLM is not the product and does not invent metrics. It assists with semantic mapping only after the target metric has been defined and deterministic discovery has produced a bounded candidate set. Deterministic gates and explicit approval control what may be published.

## Existing Foundation

The current code already:

- resolves tickers to SEC companies;
- discovers eligible Inline XBRL 10-K and 10-Q filings;
- loads filing-scoped models through Arelle;
- extracts structured facts, dimensions, reconciliation issues, calculation relationships, and validation messages before rendering;
- produces annual and latest-twelve-filed-10-Q TXT reports; and
- writes those reports atomically.

The existing report workflow remains explicitly invoked and unchanged. Normal ingestion, refresh, mapping, and frontend use will not generate TXT reports. Reports are showcase and inspection artifacts, not database inputs.

## Release Scope

### Validation release: one company, two metrics

Before the seven-metric release, ship one complete vertical slice for a single conventional issuer:

- Revenue as the direct, reported path;
- Operating Cash Flow as both reported Q1 and derived Q2/Q3 paths;
- the full five-annual and twelve-filed-10-Q window;
- durable evidence, one validated publication snapshot, the trend screen, and point/metric downloads;
- one durable background worker that recomputes the bounded company window; and
- deterministic candidate packets that can be inspected manually, without an LLM provider or review queue.

This is a product-validation boundary, not throwaway code. It must use the same evidence, mapping, derivation, publication, API, and frontend contracts as Release 1.

### Included

- A local, single-user application.
- One normalized SQLite evidence store.
- Retained original filing resources and generated artifacts.
- The seven Target Metrics listed above.
- The latest five selected Inline XBRL 10-K filings.
- The latest twelve selected exact-form Inline XBRL 10-Q filings.
- Annual and filed-quarter trend views.
- Direct mapping, deterministic candidate discovery, evidence-backed LLM recommendations, validation gates, and explicit mapping approval.
- Deterministic standalone-quarter Operating Cash Flow derivation when compatible cumulative facts exist.
- Point and metric-level evidence downloads.
- On-demand refresh through a background processing job.

### Excluded from the first release

- The remaining seven concepts from `core.txt`: Gross Profit, Cash, Debt, CapEx, Free Cash Flow, EPS, and Shares Outstanding.
- Generated Q4 values. Twelve filed 10-Q periods are not twelve consecutive fiscal quarters.
- Public hosting, multi-user access, permissions, billing, or cloud database operations.
- Automatic use of 10-K/A or 10-Q/A values. Release 1 records an amendment warning but keeps the selected exact-form base filing current until amendment support is separately designed.
- Arelle execution in API request handlers.
- Automatic acceptance of LLM suggestions.
- Automatic or scheduled TXT report generation.
- Complete EDGAR Filer Manual validation claims.
- Full-company source archives as a single download. The first release ships point and metric bundles; original retained filing resources remain individually inspectable.
- Dependency-directed incremental recomputation. The bounded filing window is recomputed first; optimization requires profiling evidence.

The excluded metrics should be addable through the same metric registry, evidence, mapping, derivation, and publication model without redesigning storage.

## Constraints and Guardrails

- A reported numeric zero is present data. It must never be treated as missing or trigger fallback.
- Report-local `E`, `D`, and `R` labels are display references, not durable database identifiers.
- Absence of a primary mapped concept is not proof that a metric was not disclosed.
- A missing classification is published only after the observed concept catalog and target-specific candidate search have completed.
- Conflicting eligible facts remain quarantined until a new source or versioned deterministic policy resolves them. Release 1 review cannot select a one-off competing value.
- Exact numeric values, units, periods, dimensions, filing identity, and source relationships must survive storage round trips.
- Arelle has shared process state. Each worker process owns one Arelle Session; processing is never parallelized with threads inside a Session.
- SEC access runs in the background with an identified user agent, caching, retry/backoff, and request rates within SEC fair-access guidance.
- LLM inputs contain compact, target-specific evidence rather than complete filing dumps. API credentials are never written to the evidence store or downloads.
- A failed refresh never replaces the last verified publication.
- Release 1 uses one durable background worker and one serialized SQLite writer. Additional workers require measured throughput need and contention tests.
- The local server binds only to loopback and rejects untrusted browser origins and unsafe state-changing requests.

## Premises and Decisions

- **Separate processing from serving.** SEC discovery, Arelle extraction, mapping, derivation, and publication run as jobs; the query API reads stored publications.
- **Use SQLite as the canonical local store.** It provides relational integrity and inspectable evidence without operating a database server. MySQL/PostgreSQL is deferred until a shared deployment requires it.
- **Retain files beside the database.** Original filing resources, exact model packets, responses, and downloadable bundles remain files whose paths, hashes, types, and lineage are registered in SQLite.
- **Publish versions, not mutable loose rows.** A refresh assembles and validates a new company publication, then atomically makes that version current. Readers never see a half-refreshed company. Older publications are either `retained` and fully queryable or `archived` and discoverable by manifest but restorable before full querying.
- **Map narrowly before asking an LLM.** The primary concept is checked first for each company, metric, and exact period. Other concepts in `mapping.txt` serve as controlled candidate seeds until their trust policy is explicitly established; an approved recommendation becomes a versioned company-specific mapping rule.
- **Keep result states distinct.** `reported`, `derived`, `unresolved`, `not_disclosed`, `conflict`, `invalid`, and `unavailable` are different outcomes. They are not collapsed into null.
- **Derive quarterly Operating Cash Flow carefully.** Compatible cumulative year-to-date facts may be subtracted to create a standalone quarter, with the formula and both source facts retained. The system does not apply this rule to instant balance-sheet facts.
- **Make evidence downloadable.** Downloads are products of a verified publication and contain a manifest that identifies every included record and artifact.
- **Release 1 contains seven metrics.** Together they exercise income-statement duration facts, balance-sheet instant facts, and the harder cumulative cash-flow case.
- **Prove two metrics before seven.** Revenue and Operating Cash Flow validate the simple and difficult data paths before LLM integration or broad metric coverage.
- **Treat amendments conservatively.** Exact-form 10-K and 10-Q filings define the Release 1 slots. Amendments are detected and surfaced as unsupported events but never silently replace facts.
- **Generate exports on demand.** A publication can be promoted without prebuilt ZIP files. Export failure affects that download request, not the integrity of the publication.

## Cross-Model Perspective

An independent cold read described the strongest version as "GitHub for financial metrics": every chart point is a versioned, inspectable claim with a semantic history and an evidence capsule. It agreed that the user's excitement comes from a simple chart plus downloadable proof, not from the LLM itself.

It also challenged the phrase "twelve quarterly periods." Filed 10-Qs mix discrete-quarter, cumulative year-to-date, and instant facts. The accepted response is to say "latest twelve filed 10-Q periods," never imply generated Q4 values, and label any standalone Operating Cash Flow subtraction as derived with both source facts retained.

The review found that a generic SQLite browser could provide useful internal inspection but only part of the product: the domain model, mapping gates, derivation lineage, publication boundary, evidence bundle, and analyst interface remain application responsibilities.

## Approaches Considered

### Approach A: Static Snapshot Portal

Generate JSON/CSV/HTML after each manual run. This is the smallest deployable shape, but refresh status, evidence review, and publication consistency would become file-management problems. Rejected because it does not provide a durable operating model.

### Approach B: Background Pipeline + Read API + Analyst Frontend

Store normalized evidence locally, process refreshes as jobs, publish verified versions, and serve them through a stable local API. Selected because it separates slow or failure-prone work from fast analyst queries while preserving end-to-end lineage.

### Approach C: Datasette-First Evidence Explorer

Expose SQLite through a generic database browser. This could be useful as an internal diagnostics surface, but it does not supply metric semantics, publication gates, mapping review, derivation explanations, or the chart-first analyst experience. Deferred as an optional internal tool.

## Recommended Architecture

```text
                         CONTROL PATH
Frontend refresh/review command
              |
              v
        Background job queue
              |
              v
SEC discovery -> retained filing -> Arelle worker process
                                      |
                                      v
                         normalized evidence records
                                      |
                                      v
 primary mapping -> candidate discovery -> optional LLM recommendation
                                      |
                          deterministic validation gates
                                      |
                                      v
                     immutable verified publication
                                      |
                         +------------+-------------+
                         |                          |
                         v                          v
                  local read API             export builder
                         |                    JSON/CSV/ZIP
                         v
                 analyst frontend
```

The control path may expose local command endpoints, but it never lets a request directly mutate published metric rows. Commands create jobs or decisions. Only the background pipeline writes evidence and publication records.

### Component Responsibilities

#### 1. Filing acquisition and archive

- Discover the configured filing window.
- Cache and retain filing resources by accession.
- Record acquisition time, source URL, content hash, form, filed date, report date, fiscal labels, and amendment status.
- Reuse unchanged resources and reject checksum or identity mismatches.

#### 2. Arelle extraction worker

- Run outside the web request path.
- Use one Arelle Session per worker process.
- Persist structured observations before any TXT rendering.
- Capture every observed filing fact needed for later cataloging, including facts excluded by current report duration/date filters.
- Preserve structured reconciliation candidates and validation relationships rather than only formatted text summaries.

#### 3. Evidence store

The normalized SQLite model should contain, at minimum:

- `companies`
- `filings`
- `processing_runs`
- `jobs`
- `concepts`
- `contexts`
- `units`
- `facts`
- `fact_dimensions`
- `reconciliation_issues`
- `reconciliation_candidates`
- `calculation_relationships`
- `validation_messages`
- `target_metrics`
- `mapping_rules`
- `mapping_recommendations`
- `mapping_decisions`
- `coverage_decisions`
- `metric_results`
- `metric_result_sources`
- `publications`
- `publication_inputs`
- `artifacts`

Facts retain the reported lexical value, an arbitrary-precision decimal representation, scale, decimals/precision metadata, and unit. SQLite floating point is not used for financial arithmetic. Display rounding is separate from stored value equivalence and a versioned decimal-arithmetic policy controls derivations. Foreign keys connect evidence instead of embedding copied objects. Stable database IDs replace report-local E/D/R labels.

SQLite runs in WAL mode with a configured busy timeout. The API primarily uses read connections and may append only short-lived command/decision rows. One background worker is the sole evidence, result, artifact, and publication writer and keeps those transactions bounded. Contention and restart tests are required before adding workers.

Filing and packet files use content-addressed storage such as `storage/objects/sha256/<hash>`. A run writes to `storage/staging/<run_id>`, verifies the dependency closure and hashes, atomically renames complete objects on the same volume, then commits their database records. Publication promotion occurs only after all referenced objects exist. Startup recovery removes abandoned staging directories and garbage-collects only unreferenced objects. Referenced evidence is never automatically deleted; when a configured quota would be exceeded, ingestion fails before promotion and leaves the current publication untouched.

An offline filing archive means the complete Arelle dependency closure, not only the primary Inline XBRL document. Referenced schemas, linkbases, taxonomy packages, and other loaded resources are logged and retained. The archive manifest maps every original absolute URI and relative reference to an object hash and records the primary entry point. Sealed replay reconstructs an Arelle-compatible directory/cache layout from that manifest, disables network access, and loads the filing from the reconstructed closure.

Canonical runtime data defaults to `%LOCALAPPDATA%\SECMetricExplorer\data`, outside the OneDrive-synchronized project directory. A custom synchronized-folder location requires an explicit unsafe-storage override and is not supported until file-locking, WAL recovery, and atomic-rename tests pass on that provider.

Release 1 performs quota preflight but does not implement archive/prune/restore. If the configured quota is insufficient, ingestion stops before staging and the user must increase the quota or relocate storage. A later retention extension may archive non-current publications while leaving their manifests discoverable. That extension must use a persisted `archiving -> archived -> pruning -> complete|failed` state machine, idempotent retry, verified restore, and startup reconciliation before deleting any local blob. The current publication, latest complete extraction, decisions, and audit manifests remain protected.

#### 4. Canonical periods and filing selection

A period slot is identified by `(company_id, fiscal_year, fiscal_period, period_kind, start_date, end_date)`, where `fiscal_period` is `FY`, `Q1`, `Q2`, or `Q3`, and `period_kind` is `duration` or `instant`. Duration metrics include `start_date`; instant metrics use only `end_date`. Ordering uses fiscal year, fiscal-period ordinal, end date, then filing date and accession as deterministic tie-breakers.

- Annual discovery groups exact-form 10-K filings by company, fiscal-year label, and report date. Within a duplicate group, the latest filed date wins, then the lexically greatest accession breaks a remaining tie. The latest five winning slots are ordered by report end date, fiscal year, filed date, and accession. Duration facts must span 300-400 days; 52/53-week years fit this range. Transition reports and fiscal-label contradictions are retained but classified `unavailable` in Release 1.
- Quarterly discovery first groups exact-form 10-Q filings into unique slots by company, fiscal year, fiscal period, and report date. Within a duplicate group, the latest filed date wins, then the lexically greatest accession breaks a remaining tie; every nonselected filing remains archived. The latest twelve winning slots are then ordered by report end date, fiscal-period ordinal, filed date, and accession. Direct quarterly duration values must span 60-120 days; instant values must be at the report end date. Six- and nine-month facts are retained as OCF derivation operands, not direct quarterly chart values.
- 10-K/A and 10-Q/A do not consume filing-window slots or replace a base filing in Release 1. Their detection creates a visible `amendment_unsupported` coverage warning.
- Each slot uses the facts from its selected base filing. Comparative facts in later filings do not silently rewrite an earlier as-filed slot.

#### 5. Target metric registry

Every metric definition is versioned and declares economic meaning, period kind, statement family, expected unit class, consolidation/dimension policy, sign convention, primary concept, and permitted derivation policy. A registry primary concept is identified by taxonomy family (`us-gaap`) plus local name across an allowlist of supported taxonomy releases; it is not matched by one literal namespace URI across all years. Each filing's exact expanded QName and namespace remain stored as evidence. An unsupported taxonomy release produces `unavailable` until the allowlist and tests are updated.

| Metric | Meaning and scope | Period | Primary concept |
| --- | --- | --- | --- |
| Revenue | Consolidated ordinary revenue, as reported | duration | `us-gaap:RevenueFromContractWithCustomerExcludingAssessedTax` |
| Operating Income | Consolidated operating income or loss, as reported | duration | `us-gaap:OperatingIncomeLoss` |
| Net Income | Consolidated net income or loss before allocation to noncontrolling interests | duration | `us-gaap:NetIncomeLoss` |
| Total Assets | Consolidated total assets | instant | `us-gaap:Assets` |
| Total Liabilities | Consolidated total liabilities | instant | `us-gaap:Liabilities` |
| Equity | Parent stockholders' equity, excluding noncontrolling interests | instant | `us-gaap:StockholdersEquity` |
| Operating Cash Flow | Consolidated net cash provided by or used in operating activities | duration | `us-gaap:NetCashProvidedByUsedInOperatingActivities` |

Values preserve the filing's sign. The reporting currency comes from a unique valid dimension-free `dei:EntityReportingCurrencyISOCode` fact for the filing. If it is absent, a unique monetary currency among otherwise eligible consolidated statement facts may be used as a recorded fallback. Contradictory DEI values or multiple fallback currencies make monetary metrics `unavailable`; different currencies are never combined. Dimension-free consolidated facts are publishable by the default policy. Dimensional totals and extension concepts require an approved, scoped mapping rule.

#### 6. Fact eligibility and precedence

The Release 1 decision matrix is conservative:

| Condition | Result |
| --- | --- |
| Nil or nonnumeric fact | retained as evidence; cannot supply a numeric result |
| Otherwise context/unit/scope-eligible fact that fails numeric or Arelle validation | `invalid`; candidate value is evidence only |
| Wrong period kind, duration range, end date, unit class, entity, or scope | ineligible candidate with recorded reason; by itself leads to `unresolved`, not `invalid` |
| Same concept/context/unit/scope and identical exact decimal value | equivalent duplicate; retain every source ID |
| Competing eligible facts with different exact decimal values | `conflict`; select neither automatically |
| Dimension-free consolidated fact satisfying all rules | eligible under the default policy |
| Dimensional or extension fact | candidate only until an approved scoped rule exists |
| Fact from a later comparative presentation | retained; does not replace the selected as-filed slot |

Release 1 intentionally treats different exact decimals as a conflict even when their reported rounding intervals overlap. A later policy may introduce precision-aware equivalence, but it must be versioned and tested.

#### 7. Metric resolution engine

For each company, Target Metric, and exact period:

1. Determine whether the metric requires a duration or instant context.
2. Check an applicable approved company-specific rule, then the registry primary concept. No other candidate publishes automatically.
3. Preserve a valid reported zero.
4. Quarantine competing eligible facts as `conflict`.
5. If unresolved, catalog observed concepts in the registry statement family using the role classifier; when no role classifies, search all numeric concepts for the slot with reduced role confidence.
6. Produce a deterministic candidate set using concept identity, labels, data type, balance, period type, presentation role, calculations, dimensions, units, and prior approved mappings.
7. If candidates exist, always persist a compact evidence packet. Invoke the LLM to rank or explain candidates only when the optional recommendation capability is enabled; otherwise leave the result unresolved for manual inspection.
8. Apply deterministic gates to the recommendation.
9. Store the recommendation as pending until explicitly approved.
10. Publish an explicit unresolved or unavailable state when the evidence supports that conclusion.

The LLM recommends a mapping for an already-defined metric. It does not define the metric, calculate the value, or publish the result.

A mapping rule key contains company, Target Metric definition version, concept QName and taxonomy namespace, form family, period kind, unit class, dimension policy, effective fiscal-period interval, and decision version. Precedence is: applicable approved company rule, registry primary concept, then no automatic match. Concepts listed as alternatives are candidate seeds only. A new taxonomy namespace, changed metric definition, expired interval, rejected candidate, or changed evidence invalidates reuse and requires reevaluation.

Presentation roles are classified deterministically by statement-family root concepts and normalized role-definition terms. Known roots such as Assets, Revenue, and NetCashProvidedByUsedInOperatingActivities anchor Balance Sheet, Income Statement, and Cash Flow families. A concept may belong to more than one role. When presentation relationships are unavailable or no role classifies, candidate discovery searches all numeric concepts for the slot and applies a lower role-confidence rank; lack of a classified role never proves absence.

`not_disclosed` is never inferred automatically in Release 1. Automatic search exhaustion produces `unresolved` with reason `no_candidate_found`. `unavailable` means extraction or archive completeness was insufficient. A user may set `not_disclosed` only after reviewing a complete successful extraction and its candidate catalog; that decision and evidence are versioned.

Result-state behavior is:

| State | Numeric API value | Chart representation | May change only through |
| --- | --- | --- | --- |
| `reported` | yes | plotted point | new publication from source/policy change |
| `derived` | yes | plotted point with derived marker | new publication from operand/policy change |
| `unresolved` | no | labeled gap | approved mapping or new evidence |
| `not_disclosed` | no | labeled gap | explicit reviewed decision or new evidence |
| `conflict` | no | conflict marker/gap | new source or versioned deterministic policy |
| `invalid` | no | invalid marker/gap | corrected source or validation policy |
| `unavailable` | no | unavailable gap | successful complete reprocessing |

Publications are immutable. A transition creates a new result and publication; it never edits the old state in place.

Slot-level state precedence is evaluated after individual fact eligibility:

1. `unavailable` when the filing archive/extraction required for the slot did not complete; other candidate evidence is retained but cannot publish.
2. `conflict` when two or more eligible valid value groups for the selected mapping have different exact decimals.
3. `reported` when exactly one eligible valid value group exists; nil or invalid observations remain warnings and do not displace the valid group.
4. `invalid` when mapped observations are otherwise context/unit/scope-eligible but all fail numeric or Arelle validation.
5. `not_disclosed` only when a versioned manual coverage decision exists for a complete extraction and candidate catalog.
6. `unresolved` when extraction is complete but no publishable value or reviewed non-disclosure decision exists.

Release 1 does not allow a user to override competing fact values. A `conflict` may change only through a new source filing or a new versioned deterministic precedence policy, followed by a new publication. Mapping decisions choose concepts, not competing values.

#### 8. Quarterly Operating Cash Flow derivation

Q1 normally uses its reported three-month cash-flow fact. Later filed quarters may be derived as:

```text
standalone Q2 = six-month YTD value - three-month YTD value
standalone Q3 = nine-month YTD value - six-month YTD value
```

Operand duration ranges are versioned rules: Q1/three-month is 60-120 days, six-month YTD is 150-220 days, and nine-month YTD is 240-310 days. Each operand must start on the same fiscal-year start date and end on the selected Q1, Q2, or Q3 report date. Under the default policy, both operands are dimension-free consolidated facts. An approved dimensional policy must require an exactly identical sorted axis/member signature across operands.

Derivation is fallback-only. When a valid eligible directly reported 60-120-day Q2 or Q3 OCF fact exists, it is published as `reported` and no derived metric value competes with it. An optional audit calculation may be stored as validation evidence; disagreement creates a validation warning but does not replace or conflict with the reported result. Derivation runs only when no eligible direct value exists.

A derivation is allowed only when both source facts:

- belong to the same entity and fiscal year;
- use the same approved concept QName, monetary unit QName, and reporting currency;
- share the exact fiscal-year start date and end on the selected Q1/Q2/Q3 report dates;
- are both dimension-free consolidated facts, or share the exact approved axis/member signature;
- are numerically valid and not quarantined by a conflict; and
- come from the selected exact-form Q1/Q2/Q3 base filings for the same fiscal year;
- use the exact same approved concept QName and taxonomy namespace; and
- are not affected by a detected unsupported amendment.

The result is stored as `derived`, never `reported`. `metric_result_sources` links both source facts and records the operator, ordered operands, exact arithmetic, checks performed, and derivation policy version. Operand failures propagate consistently: incomplete extraction yields `unavailable`, a conflicting operand yields `conflict`, an invalid-only operand yields `invalid`, and compatible valid operands that fail a derivation-specific rule yield `unresolved`. No Q4 is inferred in the first release.

#### 9. Publication service

- Build candidate results under a new publication ID.
- Verify period coverage, state validity, source lineage, mapping decisions, immutable policy versions, and artifact hashes.
- Commit the complete publication and atomically update the company's current-publication pointer.
- Keep earlier publications queryable for audit and semantic comparison.
- Leave the previous publication current if ingestion, mapping, validation, or object staging fails.

"Verified publication" means the snapshot passed integrity and lineage checks; it does not mean every metric has a numeric value. Each publication exposes coverage counts by result state. It references immutable/versioned facts, mappings, derivation policies, validation policies, and artifact hashes through `publication_inputs`; none may be edited after promotion.

`complete extraction` is a stored invariant, not a judgment call. It requires: successful discovery of the selected Inline XBRL entry point; Arelle model load without a fatal model error; enumeration of all model facts, contexts, units, concepts, and dimensions; attempted extraction of presentation and calculation relationships with an explicit success status even when zero relationships exist; completed Arelle validation capture; a complete URI-to-object archive manifest for every loaded dependency; and successful commit of all corresponding evidence rows and hashes. Any skipped stage, uncaught exception, fatal load/validation error, or missing dependency makes affected slots `unavailable` and forbids a `not_disclosed` decision. Nonfatal warnings remain evidence and do not by themselves make extraction incomplete.

#### 10. Durable jobs and local API

Jobs persist states `queued`, `running`, `retry_wait`, `succeeded`, `failed`, and `cancelled`, plus `cancel_requested` for cooperative cancellation. Each job records an idempotency key, input fingerprint, attempt count, next-attempt time, worker lease/expiry, error class, and result publication ID. A duplicate active request with the same key returns the existing job. On restart, the single worker reclaims expired leases; retries use bounded exponential backoff, and permanent validation failures do not retry automatically.

The read side exposes stable representations for companies, freshness, publications, metric series, evidence lineage, recommendation status, and downloads. Refresh, mapping, and coverage decisions use command endpoints. The API may perform narrowly scoped, short transactions only in command tables to create a job or append a decision; the worker remains the sole writer of filing evidence, metric results, artifacts, and publications. Long-running commands return a job ID; the frontend checks job status rather than holding a request open.

The server binds to `127.0.0.1`/`::1` only, uses an unpredictable per-launch session token for command requests, validates `Origin` and CSRF tokens, rejects non-JSON command bodies, and never enables permissive CORS. Artifact resolution uses database IDs, not caller-supplied filesystem paths; download names are sanitized and served with safe content-disposition headers. Secrets and raw credentials are excluded from database rows, logs, diagnostics, and bundles.

Before frontend implementation, a versioned API contract must define endpoint schemas, evidence IDs, state enums, job states, pagination, structured errors, manifest schemas, and backward-compatibility rules.

#### 11. Analyst frontend

The approved rough information architecture is:

- company and freshness controls at the top;
- the seven metrics and their current states on the left;
- annual/quarterly trend and coverage summary in the center; and
- point-level evidence and downloads in a right-side drawer.

![Approved rough wireframe](analyst_dashboard_wireframe.png)

The frontend visibly handles initial loading, no stored company, refresh in progress, verified success, partial coverage, derived values, unresolved or not-disclosed periods, conflicts, invalid facts, and refresh failure with stale-but-verified data retained.

### Download Contract

1. **Point bundle:** displayed result and the closed evidence graph reachable from it: source facts, their contexts/units/dimensions, source filing metadata, mapping/derivation/validation policy versions, reconciliation issues naming those facts, validation messages linked to them, and calculation arcs in which those facts participate.
2. **Metric bundle:** CSV trend plus JSON evidence for every period and the mapping policy version.

Every ZIP contains a machine-readable manifest with publication ID, generation time, schema version, file hashes, source accession numbers, and the export contract version. Point and metric bundles are built on demand from immutable publication inputs and may be cached by content hash. A download failure does not invalidate the publication. Exports never become inputs to the canonical database.

## Runtime Workflows

### Initial company ingestion

1. User selects a company and starts ingestion.
2. Backend creates a job and immediately returns its ID.
3. Pipeline discovers and archives the filing window.
4. Arelle worker extracts and persists filing evidence transactionally.
5. Metric engine resolves Revenue and OCF in the validation release, then all seven metrics in Release 1.
6. Release 1 may produce reviewable recommendations for unresolved candidates.
7. Publication integrity and lineage checks run.
8. A complete publication becomes current atomically.
9. Frontend loads trends and exposes point-level proof.

### Company refresh

1. Opening a company may trigger a lightweight SEC metadata check; the user may also request refresh manually.
2. If no eligible filing changed, the current publication is reused.
3. New exact-form base filings are processed without deleting historical records. Detected amendments create a visible warning and do not change metric results.
4. The bounded company filing window is recomputed. Dependency-directed recomputation is deferred until profiling proves it useful.
5. A new verified publication replaces the current pointer atomically.
6. On failure, the prior publication remains visible and the failed run is separately inspectable.

### Mapping review

1. User opens an unresolved metric recommendation.
2. Frontend shows the candidate concept, explanation, evidence citations, affected periods, and validation results.
3. Approval creates a versioned company-specific mapping rule and starts recomputation.
4. Rejection is retained so the same unsupported suggestion is not repeatedly proposed without new evidence.

### Coverage review

1. User opens an unresolved result whose extraction and candidate catalog are complete.
2. Frontend shows the searched period, statement-role coverage, observed candidate set, exclusions, and extraction-completeness checks.
3. A local command may record `not_disclosed` with reviewer, rationale, timestamp, metric/period applicability, evidence IDs, and policy version.
4. The worker recomputes the bounded company window and creates a new publication; the old unresolved result remains immutable.
5. The command is rejected when extraction/archive completeness is not proven.

## Milestones and Acceptance Criteria

### Milestone 1: Durable Evidence Storage

Extend structured extraction beyond report-eligible facts and implement SQLite migrations plus artifact registration.

Accepted when repeated ingestion is idempotent; failures leave no partial filing; exact and zero values, contexts, units, dimensions, conflicts, calculations, and validations survive round trips; content hashes verify; sealed replay succeeds with network disabled; serialized SQLite writes recover after a forced process exit; and existing report behavior remains unchanged.

### Milestone 2: Two-Metric Validation Release

Select the local frontend stack first. Then implement Revenue and Operating Cash Flow, the full result-state contract, OCF derivation, one validated publication snapshot, a read API, the approved trend/evidence screen, and point/metric downloads for one issuer. Minimum job durability includes persisted `queued`, `running`, `succeeded`, and `failed` states, idempotency keys, a worker lease, and expired-lease recovery after restart.

Accepted when both metrics are evaluated for the entire configured window; every result has one explicit state; a reported zero stays reported; conflicts cannot silently publish; Revenue links to filing facts; derived OCF links to both operands and exact arithmetic; incompatible YTD facts remain unresolved; API reads do not invoke SEC/Arelle/LLM work; and point/metric bundle hashes validate.

### Milestone 3: Seven-Metric Expansion

Add Operating Income, Net Income, Total Assets, Total Liabilities, and Equity using the versioned metric registry and fact-eligibility rules. Complete all frontend result states and the sealed acceptance corpus.

Accepted when all seven metrics are evaluated for every period; duration and instant semantics are enforced; fiscal-calendar and dimensional/conflict fixtures behave deterministically; unsupported amendments and extraction failures are visible; and every numeric result has complete source lineage.

### Milestone 4: Recommendations and Review

Create compact evidence packets, integrate one optional LLM provider behind an interface, store exact requests/responses, and implement mapping decisions.

Accepted when discovery and packet generation work without an LLM; packets are reproducible and target-specific; recommendations cite stored evidence; deterministic gates reject incompatible type, period, unit, dimension, or scope; pending recommendations cannot publish; and decisions retain user, reason, time, applicability key, and policy version.

### Milestone 5: Durable Refresh and Completed Frontend

Complete refresh commands, job recovery, recommendation review, company navigation, coverage summaries, and operational diagnostics.

Accepted when duplicate refresh requests coalesce; a no-change refresh reuses stored inputs; new base filings produce new snapshots without destroying old ones; failed and cancelled jobs recover predictably; the prior snapshot remains current on failure; every frontend state is testable; and the workflow runs locally without opening SQLite directly.

**Release 1 is complete only after Milestones 1-5 pass.** Milestone 2 is the earlier two-metric validation release; Milestone 3 alone is not a product release.

## Project-Level Success Criteria

The two-metric validation release must pass for one representative issuer with the full filing window. Release 1 additionally requires a sealed corpus with multiple issuers or filing fixtures covering: a conventional filer, extension-heavy concepts, dimensional-only candidates, conflicting/zero facts, a 52/53-week or fiscal-transition case, an unsupported amendment, compatible OCF operands, and incompatible/restated OCF operands.

4. Refreshes are idempotent, recoverable, and publication-atomic.
5. The last verified publication remains usable during SEC, Arelle, or LLM failures; export failure is isolated to the requested bundle.
6. A downloaded point or metric bundle can be inspected offline and its file hashes verified from the manifest.

8. LLM recommendations cannot publish without passing deterministic checks and explicit approval.
9. The existing TXT report workflow continues to pass its tests and remains separately invoked.

## Distribution Plan

The first release is a local application launched from the existing Python project. One local backend process serves the frontend and query API; one durable background worker process handles Arelle and serialized evidence/publication writes. SQLite and retained artifacts default to `%LOCALAPPDATA%\SECMetricExplorer\data`, outside the OneDrive project directory. The worker interface permits later process-level scaling without placing multiple evidence writers in Release 1.

Development and verification continue through `uv`; CI should run unit tests, storage migration/round-trip tests, contract tests, and a sealed filing replay. Live SEC tests remain opt-in. Packaging as a Windows executable or container is deferred until the local workflow is stable.

## Dependencies and External Constraints

- Existing `arelle-release` integration and pinned validation resources.
- Python SQLite support and a migration mechanism selected during Milestone 1 design.
- A local HTTP framework and frontend approach selected before Milestone 2.
