# SEC Inline Financials: Engineering Project Blueprint

**Audience:** Project owner  
**Application model:** Local, single-user application  
**Status:** Current blueprint; evidence storage and on-demand refresh implemented

## 1. Project objective and scope

Build a local, evidence-backed financial metric application. From a browser frontend, the user selects a company, views seven conventional financial metrics across supported annual and quarterly periods, inspects and downloads the evidence behind each result, reviews LLM mapping recommendations, and requests filing updates.

The project covers these seven Target Metrics:

- Revenue
- Operating Income
- Net Income
- Total Assets
- Total Liabilities
- Equity
- Operating Cash Flow

For each company, the application covers:

- the latest five selected Inline XBRL 10-K filings; and
- the latest twelve selected Inline XBRL 10-Q filings.

The quarterly window contains filed 10-Q periods. It does not imply generated Q4 values or twelve consecutive fiscal quarters.

This proposal defines the project's main components, responsibilities, dependencies, and delivery order. Detailed database tables, mapping rules, LLM packet schemas, API endpoints, and frontend screens belong in separate designs created when those components are implemented.

## 2. Existing foundation

### 2.1 SEC ingestion, Arelle processing, and durable evidence

The current application already:

- resolves a ticker to an SEC company;
- discovers eligible Inline XBRL 10-K and 10-Q filings;
- loads filings with Arelle;
- detaches every Arelle-exposed observation, context, unit, dimension, validation message, and supported calculation relationship before the Arelle session closes;
- retains exact filing-owned source resources, the Arelle log, and a source manifest in a SHA-256 content-addressed archive;
- stores immutable, normalized filing snapshots and versioned report classifications in SQLite; and
- extracts required narrative sections from the retained primary document into the same snapshot.

The current storage profile is `evidence-v2`. It preserves facts excluded by the report filters and records extracted, missing, or unparseable narrative sections explicitly. A compatible snapshot can be reused only after its linked artifacts pass integrity checks. A newer extraction profile creates a new snapshot without rewriting the older one.

### 2.2 On-demand inspection reports

The annual and quarterly TXT reporting service remains implemented and separate from evidence ingestion.

- Reports are generated only when the Python report API is explicitly called; there is currently no report console command.
- Reports are for the project owner's inspection.
- Company ingestion and updates do not generate reports automatically.
- Reports under `output/` are examples of the information currently produced.
- Reports are not parsed to populate the database and do not define the complete stored evidence set.

Reporting remains a separate supporting capability and is not a new implementation milestone.

## 3. Current and planned system structure

```text
Local browser frontend
        |
        | local HTTP/JSON
        v
Local Python backend
        |
        +-- evidence storage and retrieval
        +-- metric mapping and recommendation review
        +-- company ingestion and updates
        +-- evidence downloads
        |
        +--> normalized SQLite database
        +--> retained filing and evidence files
        +--> SEC discovery and Arelle processing

Explicit Python report API
        +--> in-memory SEC/Arelle report generation --> TXT inspection report
```

The browser frontend communicates with the local Python backend. The backend owns SQLite connections, filesystem access, SEC/Arelle processing, mapping operations, and downloads. This allows the frontend to use local data without coupling it directly to the database schema.

### 3.1 Evidence storage

Use one normalized SQLite database as the structured source of truth. The database contains linked records rather than one giant table or one giant company JSON document.

At a high level, storage covers:

- companies, filings, and processing runs;
- concepts, contexts, units, and all observed filing facts;
- dimensions linked to their facts;
- normalized required 10-K/10-Q narrative sections linked to the retained primary document;
- reconciliation issues and their candidate facts;
- validation messages and calculation relationships;
- metric results, mapping recommendations, and review decisions; and
- artifact metadata, paths, hashes, and versions.

Original filing resources, evidence downloads, and exact LLM evidence packets remain as files. SQLite records their identities, locations, hashes, and relationships to companies, filings, periods, and mapping decisions.

Structured SEC/Arelle results are persisted before any optional report rendering. Storage preserves exact values and provenance, distinguishes zero from missing data, and records why a fact was excluded from a report or mapping result.

The current reports guide this storage model by demonstrating selected facts, dimensional facts, reconciliation issues, validation messages, and calculation relationships. Report-local E, D, and R labels remain display references rather than permanent database identities.

### 3.2 Metric mapping

Mapping runs separately for each company, Target Metric, and exact annual or quarterly period.

The first stage performs Direct Mapping using the exact concept names maintained in `mapping.txt`. When Direct Mapping cannot populate a metric, the backend retrieves relevant stored evidence and requests an LLM Mapping Recommendation.

The recommendation is stored with its evidence and remains pending until the user approves or rejects it through the frontend. Detailed concept precedence, missing classifications, evidence selection, prompting, validation, and recommendation-reuse rules will be defined in the separate mapping design.

### 3.3 Update mechanism

Updates occur through local application use rather than a background schedule.

- A company request first checks stored refresh state.
- SEC discovery runs only when the annual or quarterly check is due, refresh is forced, evidence is missing, or an active snapshot lacks the current narrative-section profile.
- A complete current window returns `reused_local` without SEC or Arelle access.
- The planned frontend will expose company access and a manual refresh action over this backend behavior.
- When no eligible filing changed, the backend reuses the stored company data.
- When new eligible filings are found, the backend stores the new evidence and refreshes affected metric results.
- Earlier evidence and mapping decisions remain retained for traceability.
- Ingestion and updates do not generate TXT inspection reports.

Current transaction, retry, snapshot-versioning, active-window, and fallback rules are defined in `ingestAndUpdate.txt` and `evidence-storage.md`. Mapping recommendation invalidation remains a Milestone 2/3 design concern.

### 3.4 Frontend

The frontend is a core project component and the main interface for the completed application. It is served locally and communicates with the Python backend through a local API.

At blueprint level, it provides:

- company selection and local data status;
- annual and quarterly views of the seven Target Metrics;
- visible resolved, missing, conflicting, and pending-review states;
- access to the filing and fact evidence behind each result;
- downloadable evidence artifacts;
- approval or rejection of LLM Mapping Recommendations; and
- manual refresh with update status.

The frontend does not open or query SQLite directly. The backend supplies stable responses and controls access to retained artifacts.

## 4. Runtime workflows

### 4.1 First company ingestion: implemented foundation plus planned mapping

1. A caller submits a company ticker through the ingestion CLI or Python API.
2. The backend initializes storage, resolves the company, and selects its filing window.
3. Each selected filing is processed in its own Arelle session.
4. All exposed observations, supporting evidence, retained resources, and required narrative-section records are stored per filing.
5. The backend publishes the active five-annual/twelve-quarter window after processing and returns per-filing outcomes.
6. In Milestone 2, Direct Mapping will run for the seven Target Metrics for every supported period.
7. In Milestone 3, unresolved metrics will enter the LLM recommendation and human-review workflow.
8. In Milestone 5, the frontend will display stored metric results and evidence.

This workflow does not generate a TXT inspection report.

### 4.2 Company access and update: implemented

1. A stored-company request checks next-check dates and evidence completeness locally.
2. If the window is complete and no check is due, the backend returns `reused_local` without SEC or Arelle access.
3. A due, forced, missing-evidence, or missing-section request refreshes SEC metadata and processes the selected filing window.
4. Compatible snapshots are artifact-verified and reused; missing or newer-profile snapshots are extracted and stored independently.
5. The backend publishes the active window only after the run and retains earlier snapshots and inactive filing metadata.
6. The result reports `checked_no_update`, `updated`, or `refresh_failed_using_local_data` as applicable. Metric refresh begins after Milestone 2 is implemented.

### 4.3 Inspection report generation

1. The project owner explicitly calls `sec_inline_financials.service.generate_reports` or `generate_report`.
2. The current SEC/Arelle report workflow runs unchanged.
3. The resulting annual and quarterly TXT files are used for manual inspection.

This workflow remains separate from normal ingestion, updates, and frontend use.

## 5. Implementation sequence

### Milestone 1: Durable evidence storage — implemented

Structured extraction retains all observed filing facts, normalized SQLite evidence, artifact tracking, report replay, and profile-v2 narrative sections.

This milestone proves that filing evidence can be stored and reloaded without losing identities, values, dimensions, conflicts, validation evidence, or calculation relationships. Repeated ingestion must be safe, failed imports must not leave partial results, and existing report behavior must remain unchanged.

### Milestone 2: Incremental evidence updates — implemented

Company-access checks and manual refresh behavior process selected eligible filings, publish active windows, and retain historical evidence. Refreshing mapped metric results remains dependent on Milestone 2.

This milestone proves that no-change checks reuse stored data, new filings extend the evidence history, failed updates preserve the last usable result, and updates never generate inspection reports automatically.

### Milestone 3: Direct Mapping — planned next

Implement period-by-period lookup for the seven Target Metrics using `mapping.txt` and persist each metric result with links to its filing evidence.

This milestone proves that all seven metrics are evaluated for every supported period and that resolved, zero, missing, and conflicting states remain distinguishable without generating reports.

### Milestone 4: LLM recommendations and human review — planned

Build target-specific evidence retrieval, store exact model requests and responses, and support approval or rejection of Mapping Recommendations.

This milestone proves that each recommendation is reproducible, cites retained evidence, and cannot become an accepted mapping without user approval.

### Milestone 5: Local frontend — planned

Build the browser interface and local backend API over the completed storage, mapping, review, and update capabilities.

This milestone proves that the user can select a company, view all seven metrics, inspect and download evidence, review Mapping Recommendations, and request refreshes without opening SQLite directly.

## 6. Project-level completion criteria

The project is complete when the local application can:

1. persist all observed filing facts for the defined filing window in one normalized SQLite database;
2. evaluate the seven Target Metrics for every supported period;
3. trace every metric result to its filing and evidence;
4. produce evidence-backed Mapping Recommendations and require human approval;
5. detect and process new eligible filings on demand;
6. expose metrics, evidence, downloads, review actions, and refresh controls through the local frontend; and
7. keep the existing explicitly invoked inspection-report workflow unchanged and separate.

## 7. Boundaries and follow-up designs

This blueprint does not define:

- financial metrics outside the seven-metric project scope;
- public hosting or multi-user operation;
- automatic or scheduled report generation;
- table-by-table SQLite schema and migration details;
- detailed mapping and missing-data policies;
- LLM provider selection, prompts, or packet limits;
- API endpoint contracts or frontend screen layouts; or
- amendment, retry, and failure-recovery rules beyond the high-level boundaries above.

Each milestone should receive its focused design before implementation. This blueprint changes only when the project's major scope, component boundaries, or delivery order changes.
