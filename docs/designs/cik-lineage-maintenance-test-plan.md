# Test Plan: CIK Lineage Maintenance

## Affected Commands

- `sec-inline-financials-lineage SUCCESSOR_CIK PREDECESSOR_CIK` — verify the complete
  preview, confirmation, relationship creation, predecessor ingestion, retry, and exit-code
  behavior.
- Existing company ingestion and Direct Mapping commands — verify that single-CIK companies
  remain unchanged and predecessor filings map under their own registrant CIK.

## Key Interactions to Verify

- Enter padded and unpadded CIKs and confirm both normalize to ten digits.
- Confirm the successor already belongs to a stored company lineage.
- Confirm the output shows the canonical company, existing lineage, both SEC legal names, and
  the exact predecessor-to-successor edge.
- Enter `y` and verify the edge commits before predecessor ingestion begins.
- Enter `n`, blank input, EOF, or interrupt and verify no database write or ingestion starts.
- Enter invalid confirmation text and verify the command re-prompts.
- Rerun an existing exact edge and verify no duplicate lineage row is created and ingestion
  retries.
- Add an older predecessor through the current oldest member and verify the chain becomes
  `older -> predecessor -> current`.
- Retrieve overlapping periods and verify the nearest/current registrant wins.
- Retrieve a period absent from the current registrant and verify the nearest predecessor fills
  it.
- Verify annual and quarterly windows improve independently.
- Verify Direct Mapping accepts a predecessor filing whose context CIK matches that filing's
  registrant CIK.

## Edge Cases

- Invalid, zero, negative, nondigit, or longer-than-ten-digit CIK.
- Unknown successor CIK.
- Same CIK supplied twice.
- Predecessor CIK already owned by another company.
- Proposed self-link, cycle, branch, merge, disconnected graph, or non-oldest successor.
- SEC timeout, malformed JSON, blank legal name, or response CIK mismatch before confirmation.
- Concurrent lineage change after preview but before confirmation.
- Exact edge already exists.
- SEC history request fails after the edge commits.
- Eligible 10-K or 10-Q row has a missing or malformed filing/report date.
- A current-entity filing exists but processing fails; ensure the same-period predecessor is not
  substituted.
- A predecessor filing fails Arelle processing, artifact capture, or database storage.
- A partial candidate has fewer usable snapshots than the stored form window.
- One form improves while the other form fails or remains unchanged.
- A filing accession is rediscovered with different registrant or archive-owner identity.
- Purging a lineage-enabled company leaves unrelated company data intact.

## Critical Paths

1. New link: preview names and edge -> approve -> commit edge -> ingest predecessor -> publish
   stronger snapshot-backed windows -> run Direct Mapping -> retrieve combined periods.
2. Cancellation: preview -> decline or interrupt -> prove database and artifact store unchanged.
3. Retry: approve link -> force ingestion failure -> prove edge retained -> rerun -> prove
   idempotent edge and successful ingestion.
4. Chain extension: existing `B -> A` -> invoke with successor B and predecessor C -> approve ->
   retrieve in `A, B, C` priority order.
5. Conflict: predecessor already belongs elsewhere or would create an invalid graph -> reject
   before confirmation/write.
6. Migration: copy version-6 fixture -> migrate -> verify membership/provenance backfill,
   foreign keys, integrity, existing ingestion, and purge.

## Test Environment

- Required suite uses fixture SEC JSON, temporary SQLite databases, and temporary artifact roots.
- Default tests make no network requests.
- An optional `live` smoke test may contact SEC in an isolated evidence root and must never
  print the configured User-Agent.
