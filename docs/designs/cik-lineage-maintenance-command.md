## Problem Statement

The current ingestion path assumes that one canonical company has one SEC CIK. That fails when
a legal successor registrant continues the public-company history while older 10-K and 10-Q
filings remain under a predecessor CIK.

Add one maintenance command that accepts an existing successor CIK and a new predecessor CIK,
shows the SEC legal name associated with each CIK, asks the project owner for a simple `y/n`
confirmation, records an explicit predecessor-to-successor edge, and immediately invokes the
ordinary company-ingestion pipeline. Each CIK remains a distinct legal entity.

The default 5-annual/12-quarterly filing window is selected current-to-oldest. A filing from a
predecessor fills a requested period only when every higher-priority registrant is missing that
period. If both entities filed for the same period, the higher-priority current entity wins.

## Scope Decision

The engineering review reduced version one to the smallest implementation that meets the
maintenance need:

- ship link-only lineage maintenance;
- reuse the existing active-window tables and publication flow;
- reuse the existing SEC, Arelle, evidence-storage, classification, and Direct Mapping pipeline;
- add only the identity and lineage storage required for distinct legal registrants;
- defer unlink, immutable graph-version history, and a second active-window publication system.

This keeps the command corrective and auditable without creating a parallel ingestion or
retrieval architecture.

## NOT in Scope

- **Unlink or reassignment command:** correction semantics can invalidate an exposed window and
  need a separate design; version one only adds exact edges.
- **Lineage-version history:** the command needs stale-preview protection, not a permanent copy
  of every graph state.
- **A second active-window publication subsystem:** the existing active tables can safely hold
  the best snapshot-backed annual and quarterly windows.
- **Persisted coverage/audit publications:** run outcomes and ordinary processing records are
  sufficient for this local maintenance workflow.
- **Fabricated effective dates:** the two CIK inputs provide no defensible transition date.
- **Automatic relationship proof or inference:** no ticker, name, former-name, accession, or LLM
  heuristic creates an edge.
- **Noninteractive approval:** version one has no `--yes`, environment override, or API bypass.
- **Full SEC archive ingestion:** the command fills the configured requested window; it does not
  ingest every filing ever submitted.
- **Foreign-issuer forms, amendments, IFRS expansion, and joint-registrant filings:** exact Inline
  XBRL `10-K` and `10-Q` remain the supported scope.
- **Background jobs, queueing, UI, or remote retrieval:** the command is a local synchronous
  package entry point, and application retrieval remains local.
- **TODOS.md changes:** no `TODOS.md` exists, and deferred product features are intentionally
  documented here rather than added as vague backlog items.

## Constraints and Invariants

- The first CIK must already belong to exactly one stored company lineage.
- On the first link, that existing successor is normally `companies.cik`. To extend a chain,
  the operator supplies the current oldest member as the successor.
- The predecessor must be new to that lineage unless the exact edge already exists.
- A CIK may belong to only one canonical company.
- Edges point from predecessor to successor and form one connected linear chain anchored at
  `companies.cik`.
- Branches, merges, cycles, self-links, disconnected members, and cross-company ownership fail
  closed.
- CIKs are normalized once to ten decimal digits. Zero, nondigits, and values longer than ten
  digits fail before SEC access.
- SEC legal names are display data. Normalized CIKs are identity keys.
- The command stores no authorization source, confirmer identity, prompt response, attestation,
  or effective date.
- Only `y` or `Y` commits. `n`, `N`, blank, or EOF cancels; invalid text re-prompts;
  interruption exits without mutation.
- The lineage edge commits before ingestion. Any later ingestion failure retains the edge and
  produces an explicit retry command.
- A selected current-entity filing that fails processing is not replaced by a predecessor filing
  for the same period. Fallback is for absent periods, not processing failures.
- Existing snapshots, raw facts, XBRL contexts, and artifact bytes remain immutable.

### Graph invariant

```text
oldest source                                      canonical current sink

CIK C  ──predecessor-of──>  CIK B  ──predecessor-of──>  CIK A
  ^                                                     ^
  |                                                     |
new predecessor                                   companies.cik

Allowed: one source, one sink, one path
Rejected: branch, merge, cycle, disconnected member, cross-company CIK
```

If the stored lineage is `B -> A` and the operator later adds C, the command is invoked with
`B C` and creates `C -> B -> A`. Invoking `A C` would create a branch and is rejected.

## Operator Journey

Add this package entry point:

```text
sec-inline-financials-lineage SUCCESSOR_CIK PREDECESSOR_CIK
```

Initial-link example:

```text
$ uv run --no-sync sec-inline-financials-lineage 0002115436 0000034088

Canonical company
  ExxonMobil Holdings Corporation (current CIK 0002115436)

Existing lineage
  0002115436  ExxonMobil Holdings Corporation

Proposed direct edge
  0000034088  Exxon Mobil Corporation
       ->
  0002115436  ExxonMobil Holdings Corporation

Create this lineage and ingest the predecessor's filings? [y/n]:
```

Before the prompt, the command displays:

1. the canonical stored company and current CIK;
2. the complete existing lineage;
3. the fresh SEC legal names for both supplied CIKs;
4. the exact direct edge that will be added; and
5. whether the edge is new or already present.

Input behavior:

- `y` or `Y`: revalidate, save the edge if needed, then ingest;
- `n`, `N`, blank, or EOF: print `Cancelled; no changes made.` and exit 0;
- other text: print `Please enter y or n.` and ask again;
- `KeyboardInterrupt`: print cancellation and exit 130.

There is no noninteractive bypass. An already-present exact edge still requires confirmation;
approval retries the ordinary ingestion pipeline without inserting duplicate rows.

## Architecture

### End-to-end flow

```text
two CIK arguments
      |
      v
shared normalize_cik()
      |
      +-- invalid ------------------------------> clear error, no SEC, no write
      |
      v
load stored lineage by successor CIK
      |
      +-- absent/conflict/cycle ----------------> clear error, no write
      |
      v
SecClient.resolve_registrant() for both CIKs
      |
      +-- timeout/CIK mismatch/blank name ------> clear error, no write
      |
      v
typed LineagePatchPlan + display + y/n
      |
      +-- cancelled/interrupted ----------------> no write, no ingestion
      |
      v
BEGIN IMMEDIATE -> reload -> compare state hash -> insert exact edge -> commit
      |
      +-- stale/conflicting writer -------------> clear error, no partial write
      |
      v
shared CompanyIngestionService core
      |
      +-- SEC/Arelle/storage failure -----------> edge retained, nonzero, retry command
      |
      v
snapshot-backed per-form publication -> Direct Mapping -> local retrieval
```

Inline ASCII comments should accompany the graph validation in `company_lineage.py` and the
current-first selection/publication pipeline in `company_ingestion.py`. The CLI does not need
an inline diagram because it contains no business branching beyond prompt handling.

### Domain and service boundary

Create `company_lineage.py` as the single lineage domain module. It owns:

```python
@dataclass(frozen=True)
class RegistrantIdentity:
    cik: str
    legal_name: str


@dataclass(frozen=True)
class LineageEdge:
    predecessor_cik: str
    successor_cik: str


@dataclass(frozen=True)
class CompanyLineage:
    company_id: int
    canonical_current_cik: str
    current_to_oldest: tuple[RegistrantIdentity, ...]
    edges: tuple[LineageEdge, ...]
    state_hash: str


@dataclass(frozen=True)
class LineagePatchPlan:
    company_id: int
    successor: RegistrantIdentity
    predecessor: RegistrantIdentity
    before: CompanyLineage
    after: CompanyLineage
    expected_state_hash: str
    already_present: bool


class LineageMaintenanceService:
    def preview_link(self, successor_cik: str, predecessor_cik: str) -> LineagePatchPlan: ...
    def apply_link(self, plan: LineagePatchPlan) -> Literal["created", "already_present"]: ...
    def apply_and_ingest(self, plan: LineagePatchPlan) -> LineageMaintenanceResult: ...
```

The module also exposes the one shared `normalize_cik()` helper. The CLI imports it rather than
implementing another parser.

`lineage_cli.py` stays thin: parse two arguments, construct dependencies, render the typed
plan, read `y/n`, call the service, render the result, and return an exit code. It contains no
SQL, graph traversal, SEC selection, or predecessor-specific ingestion.

### Transactional preview and apply

`preview_link()`:

1. normalizes both CIKs and rejects equality;
2. finds the canonical company through the existing successor membership;
3. loads the full ordered chain and validates its invariants;
4. requires the supplied successor to be the chain's oldest member unless the exact edge already
   exists;
5. rejects a predecessor owned by another company or attached through another edge;
6. resolves both current SEC legal names;
7. constructs the exact before/after graph; and
8. computes SHA-256 over canonical JSON containing the canonical current CIK, ordered members,
   and ordered edges.

`apply_link()` starts the existing `BEGIN IMMEDIATE` write transaction, reloads the graph,
recomputes the state hash, and repeats every invariant. A hash mismatch or different edge state
raises a stale-plan conflict. The transaction performs no network or Arelle work.

An exact active edge is an idempotent no-op. There are no inactive/reactivated states in version
one because unlink is not part of this design.

### Storage migration

Add migration `0007_cik_lineage.sql` without rewriting earlier migrations:

```text
company_ciks(
  company_id INTEGER NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  cik TEXT NOT NULL UNIQUE CHECK(length(cik) = 10),
  legal_name TEXT NOT NULL,
  associated_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY(company_id, cik)
)

company_cik_transitions(
  company_id INTEGER NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  predecessor_cik TEXT NOT NULL,
  successor_cik TEXT NOT NULL,
  created_at TEXT NOT NULL,
  CHECK(predecessor_cik <> successor_cik),
  PRIMARY KEY(company_id, predecessor_cik, successor_cik),
  UNIQUE(company_id, predecessor_cik),
  UNIQUE(company_id, successor_cik),
  FOREIGN KEY(company_id, predecessor_cik)
    REFERENCES company_ciks(company_id, cik) ON DELETE CASCADE,
  FOREIGN KEY(company_id, successor_cik)
    REFERENCES company_ciks(company_id, cik) ON DELETE CASCADE
)

filing_provenance(
  filing_id INTEGER PRIMARY KEY REFERENCES filings(id) ON DELETE CASCADE,
  registrant_cik TEXT NOT NULL REFERENCES company_ciks(cik) ON DELETE RESTRICT,
  archive_owner_cik TEXT NOT NULL REFERENCES company_ciks(cik) ON DELETE RESTRICT,
  recorded_at TEXT NOT NULL
)
```

Required indexes cover transitions by company and provenance by
`(registrant_cik, filing_id)` and `(archive_owner_cik, filing_id)`. The unique CIK constraint
prevents cross-company ownership at the database boundary. The service additionally verifies
that filing provenance belongs to the filing's canonical company before every upsert.

Migration backfill:

- insert each legacy `companies.cik/current_name` as its company's initial `company_ciks` row;
- insert one `filing_provenance` row for each legacy filing using that company's current CIK as
  both registrant and archive owner;
- leave all filing, snapshot, fact, mapping, and artifact payloads unchanged; and
- require `PRAGMA foreign_key_check` and `PRAGMA integrity_check` to pass.

After migration, ordinary single-CIK company creation and filing upsert atomically maintain the
same membership and provenance records. Filing provenance is immutable accession metadata:
rediscovering an accession with a different registrant or archive owner raises
`FilingMetadataError`.

Company purge is verified against the new foreign keys. It deletes filings and provenance before
the company cascade removes transitions and memberships; unrelated companies remain untouched.

### Filing identity

Extend the core immutable `Filing` model with required:

```python
registrant_cik: str
archive_owner_cik: str
```

`registrant_cik` is the legal entity whose filing is being processed.
`archive_owner_cik` is the CIK used in the SEC Archives URL. These values are carried from SEC
discovery through filing upsert, evidence snapshots, mapping input, and active-window
fingerprints. They are never rewritten to the canonical company's current CIK.

Direct Mapping compares each fact context entity identifier with that filing's
`registrant_cik`. An unrelated CIK still fails entity validation.

### SEC name resolution, discovery, and caching

Extend `SecClient` with:

```python
def resolve_registrant(self, cik: str) -> RegistrantIdentity: ...

def discover_company_window(
    self,
    lineage: CompanyLineage,
    *,
    annual_count: int,
    quarterly_count: int,
) -> DiscoveredCompanyWindow: ...
```

The client keeps a request-scoped dictionary keyed by SEC JSON URL. Within one command, legal
name resolution and annual/quarterly discovery reuse the same submissions response, and each
history URL is fetched at most once. The cache is discarded when the command ends; later runs
contact SEC again.

`resolve_registrant()` requires the top-level response CIK to match the requested normalized
CIK and requires a nonblank top-level legal name.

Discovery processes both forms in one pass per registrant:

1. traverse current-to-oldest;
2. parse exact Inline XBRL `10-K` and `10-Q` rows;
3. use annual slot `Y:{report_date.year}` and quarterly slot
   `D:{report_date.isoformat()}`;
4. within one member and slot, choose greatest `(filing_date, accession)`;
5. fill only still-empty slots, so the nearest/current registrant wins overlaps;
6. deduplicate globally by accession; and
7. stop history and predecessor traversal when both requested form counts are satisfied.

Rows clearly outside the requested exact form or not Inline XBRL are ignored. Once a row is
eligible, missing, misaligned, or invalid required metadata raises `DiscoveryError` identifying
the CIK and row or accession. Eligible filings are never silently discarded.

A fetch failure at one member stops lower-priority traversal because priority across that gap
cannot be proven. Already discovered higher-priority filings may still be processed, but the
command exits nonzero and reports the failed CIK/URL.

### Shared ingestion entry point

Refactor `CompanyIngestionService` so the public ticker method and the maintenance command both
delegate to one internal resolved-company implementation:

```text
ingest_company(ticker, ...)
      -> resolve ticker/current company
      -> _ingest_resolved_company(company_id, lineage, ...)

ingest_company_cik(successor_cik, ...)
      -> load exact stored company/lineage
      -> _ingest_resolved_company(company_id, lineage, ...)
```

The maintenance command does not resolve a ticker and does not duplicate ingestion logic. It
discovers the whole requested current-first window, but completed current-company snapshots are
reused rather than downloaded or processed again. New predecessor accessions go through the
ordinary `EvidenceIngestionService` and Arelle processor.

The relationship transaction commits before calling this core. A crash or failure afterward
leaves an exact edge that a rerun recognizes as `already_present`; approval then retries
ingestion.

### Existing active-window publication

Do not add publication/version/head tables. Strengthen the existing
`publish_filing_window()` behavior independently for `10-K` and `10-Q`:

1. form a candidate only from selected filings that have reusable or newly successful snapshots;
2. never mark a filing active without an `active_filing_snapshots` binding;
3. compare candidate and stored form windows by
   `(usable_snapshot_count, ordered_(report_date, filing_date, accession)_desc)`;
4. replace the stored form only when the candidate tuple is strictly greater;
5. treat an equal tuple as an idempotent no-op; and
6. preserve a stronger stored annual or quarterly window when the other form improves or the
   current run partially fails.

The active flags, ranks, and snapshot bindings for one form update atomically. A zero-usable
candidate never replaces an existing window. Processing failures are reported by the run result
but do not become a reason to substitute a same-period predecessor.

### Retrieval behavior

Application retrieval remains local:

```text
requested active-window period
      |
      v
published snapshot-backed window
      |
      +-- current registrant has period ------> use current filing
      |
      +-- otherwise nearest predecessor has it -> use predecessor filing
      |
      +-- no lineage member has it -----------> period remains absent
```

The current-first decision is made deterministically during discovery/publication. Retrieval
does not contact SEC or run Arelle. Raw facts and XBRL context identifiers remain exactly as
filed, while the selected filing retains canonical company, registrant CIK, and archive-owner
CIK.

## Result and Exit Semantics

| Condition | Relationship | Ingestion | Exit |
|---|---|---|---|
| invalid CIK or successor absent | unchanged | not started | 1 |
| SEC name lookup fails or response CIK mismatches | unchanged | not started | 1 |
| cross-company conflict, cycle, branch, merge, or stale plan | unchanged | not started | 1 |
| operator answers no/blank/EOF | unchanged | not started | 0 |
| operator interrupts | unchanged | not started | 130 |
| exact edge already exists and operator answers yes | unchanged/idempotent | retried | ingestion result |
| all requested slots usable | retained | complete | 0 |
| clean historical shortfall with usable evidence | retained | partial warning | 0 |
| no eligible historical filings | retained | empty warning | 1 |
| SEC fetch or eligible-metadata failure | retained | retryable failure | 1 |
| selected filing processing/storage failure | retained with valid evidence | retryable failure | 1 |

Every nonzero post-commit message must say that the relationship was retained and print the exact
rerun command. It must not imply that the lineage transaction rolled back.

## Failure Modes

| Code path | Realistic failure | Test | Handling | Operator visibility |
|---|---|---|---|---|
| CIK parsing | nondigits, zero, or overflow | unit | reject before SEC | explicit invalid-CIK message |
| Stored lookup | successor is absent or owned ambiguously | integration | fail closed | explicit stored-lineage error |
| SEC name preview | timeout, blank name, response CIK mismatch | fixture integration | no mutation | exact CIK/URL error |
| Confirmation | invalid text, EOF, interruption | CLI | re-prompt or cancel | explicit cancellation |
| Graph apply | concurrent writer changes lineage after preview | SQLite integration | `BEGIN IMMEDIATE` plus state-hash revalidation | stale-plan error |
| Graph validation | cross-company CIK, branch, merge, or cycle | unit + integration | reject transaction | exact conflicting edge/company |
| Post-commit handoff | process exits before ingestion starts | service integration | edge remains; rerun is idempotent | retry command |
| SEC discovery | history request fails mid-chain | fixture integration | stop lower-priority traversal | failed CIK/URL and nonzero exit |
| SEC metadata | eligible 10-K/10-Q has invalid date/columns | unit | raise; never silently skip | row/accession diagnostic |
| Filing processing | Arelle, taxonomy, artifact, or storage failure | integration | retain valid snapshots and edge | per-accession failure |
| Window publication | partial candidate is weaker than stored window | store integration | preserve stronger per-form window | warning plus retained counts |
| Mapping | predecessor fact carries unrelated entity CIK | regression | reject fact against filing registrant | mapping failure reason |
| Purge | new foreign keys block or leak company data | migration/purge integration | ordered delete and cascade | transaction rollback/error |
| Request cache | repeated URL or long history chain | unit | one in-memory value per visited URL; bounded traversal | no silent behavior |

Every failure has both an explicit handling path and planned automated coverage. There are no
known silent, untested critical gaps.

## Performance Requirements

- A command-scoped cache fetches each SEC JSON URL at most once.
- Annual and quarterly candidates are parsed together per lineage member.
- History traversal stops only when both form windows are satisfied or history is exhausted.
- Candidate rows are deduplicated by accession before processing.
- The store loads the lineage and active per-form coverage in batched queries; no per-filing
  lineage lookup is permitted.
- Existing indexes serve active-window reads; new indexes serve transition and provenance lookup.
- SEC requests remain sequential and deterministic. Do not add parallel request fan-out.
- No HTTP response is cached across commands.

## Worktree Parallelization Strategy

| Step | Modules touched | Depends on |
|---|---|---|
| Contract seed | domain models, core filing model | — |
| Storage lane | storage, migrations, storage tests | Contract seed |
| SEC lane | SEC client, discovery tests | Contract seed |
| Mapping lane | mapping models, Direct Mapping, mapping tests | Contract seed + storage provenance |
| Integration lane | ingestion service, maintenance service, CLI, integration tests | Storage + SEC + Mapping |
| Verification lane | runbook/design docs, full gates, optional live smoke | Integration |

Parallel lanes:

- **Seed:** land the CIK/provenance contracts first.
- **Lane A:** storage migration -> lineage persistence -> store tests.
- **Lane B:** SEC name/cache/combined discovery -> SEC tests. Lane B can run in parallel with A
  after the seed contract.
- **Lane C:** mapping identity changes after A exposes provenance.
- **Lane D:** shared ingestion core -> maintenance service/CLI -> fixture E2E after A+B+C merge.
- **Lane E:** full gates and optional live acceptance after D.

Execution order: Seed; launch A and B in parallel; merge A+B; run C; then D; then E.

Conflict flags:

- Seed and B both touch the core `Filing` contract if started together; keep Seed separate.

Migration 0007 is additive; never remove its ledger row manually. A code rollback may ignore the
new tables but cannot safely remove a mistaken relationship. Because unlink is explicitly
deferred, correction before a future unlink design is restore-from-backup or a separately
reviewed repair procedure—not ad hoc SQL.

The lineage transaction and ingestion are deliberately separate. If ingestion fails, rerun the
same command and approve the already-present edge; do not delete or recreate it.

## Success Criteria

- Exactly two CIK arguments are normalized deterministically.
- The first CIK already belongs to the stored lineage and the second is its exact new
  predecessor.
- Before mutation, the operator sees both SEC legal names, both CIKs, the existing lineage, and
  the exact proposed edge.
- Only `y/Y` authorizes the link and ingestion; every cancellation path writes nothing.
- Each CIK remains a distinct legal entity and each edge is explicit.
- Cross-company ownership, self-links, branches, merges, cycles, ambiguous chains, and stale
  previews fail without partial writes.
- Concurrent writers serialize through the existing `BEGIN IMMEDIATE` transaction.
- Exact reruns create no duplicate lineage, filing, snapshot, or mapping rows.
- Ingestion failure after commit retains the edge and prints a retryable nonzero result.
- Current-first selection fills only absent annual-year or quarterly-date slots from the nearest
  predecessor.
- A selected filing failure never triggers predecessor substitution for that same slot.
- Every selected filing retains immutable registrant and archive-owner CIKs.
- Direct Mapping validates against the filing registrant rather than the canonical current CIK.
- Only snapshot-backed filings become active; annual and quarterly windows improve independently.
- A weaker partial candidate never replaces a stronger stored form window.
- Eligible malformed SEC rows fail explicitly rather than disappearing silently.
- Each SEC JSON URL is fetched once at most per command.
- Migration/backfill, foreign keys, integrity checks, purge, and existing single-CIK behavior pass
  deterministic tests.
- The complete offline pytest, Ruff, mypy, and diff-check gates pass before persistent use.
