## Problem Statement

The current ingestion path assumes that one canonical company has one SEC CIK. That fails
when a legal successor registrant keeps the public-company identity while historical 10-K and
10-Q filings remain under a predecessor CIK.

Add a maintenance command that accepts the canonical current CIK and one predecessor CIK,
shows the SEC legal names associated with both identities, asks the project owner for `y/n`
confirmation, records an explicit predecessor-successor edge, and immediately runs the
ordinary company-ingestion workflow. Each CIK remains a distinct legal registrant. Filing
selection searches the current CIK first and fills unoccupied requested positions from the
operator-confirmed stored lineage.

## What Makes This Cool

Two identifiers repair an otherwise invisible historical-data break. Before committing, the
tool shows the existing lineage and exact before/after graph, so the operator can see which
legal entity will supply which missing history. Afterward the normal application retrieves a
single evidence-backed company window without erasing the registrants that actually filed each
report.

## Constraints

- The active `gstack` checkout is currently single-CIK and contains migrations through version
  6. The earlier validated lineage implementation was not committed and must be reconstructed.
- The current CIK must already identify exactly one stored canonical company.
- The predecessor CIK may not equal the current CIK, belong to another canonical company,
  create a cycle, or conflict with an existing edge.
- The project owner is the only authorized operator. The link and unlink maintenance commands,
  both routed through `LineageMaintenanceService`, are the only supported lineage mutation
  paths. Do not add authorization, attestation, `confirmed_by`, or persisted confirmation data.
- Resolve legal names from SEC submissions metadata before any database write. Names help the
  human confirm the identities; CIKs, not names, are the identity keys.
- The two-input command supplies no legal effective date. Do not infer or fabricate one.
- The confirmation interface is intentionally simple: only `y` or `Y` proceeds. `n`, `N`,
  blank input, EOF, or interruption exits cleanly without writes or ingestion. Other input
  re-prompts.
- A confirmed lineage relationship is durable independently of ingestion success.
- Existing immutable filing snapshots and artifacts must not be rewritten.
- User-facing retrieval remains local. It never contacts the SEC or runs Arelle synchronously.
- Exact-form Inline XBRL `10-K` and `10-Q` remain the supported filing scope.
- Foreign-issuer forms, IFRS mapping, candidate discovery, LLM inference, and a lineage UI are
  outside this change.

## Premises

- One shared lineage model is the only source of truth. The maintenance command must not create
  a parallel association system.
- The current CIK is the lookup key for the canonical company. When that company already has an
  unambiguous chain, the new predecessor attaches behind the oldest member; the preview shows
  the actual edge. Ambiguous graphs fail closed.
- Without an effective date, selection uses deterministic current-first gap filling. Current
  registrant filings win a period collision; predecessors contribute only still-missing annual
  report years or quarterly report dates.
- A lineage gap means an eligible filing period is absent. A selected filing that later fails
  download, taxonomy loading, Arelle processing, or artifact capture remains a filing-specific
  failure and does not trigger predecessor substitution.
- Relationship creation and ingestion are separate operations. The edge commits first; an
  ingestion failure preserves the edge and valid evidence, returns nonzero, and can be retried
  idempotently.
- Partial windows remain usable. Available filings continue through Arelle, evidence storage,
  report classification, and independent per-form Direct Mapping. Absent periods never create
  synthetic metric rows.

### Graph invariant

Each canonical company has exactly one connected linear chain of active registrants. Edges point
from predecessor to successor. The current CIK is the unique sink and has no successor; the
oldest CIK is the unique source and has no predecessor; every intermediate member has exactly
one predecessor and one successor. Active branches, merges, cycles, disconnected members, and
orphan memberships are invalid. Database uniqueness constraints prevent multiple active incoming
or outgoing edges, while domain validation proves connectedness and acyclicity before every
write.

## Cross-Model Perspective

The independent cold review proposed a typed `LineagePatchPlan`: compute the exact before/after
graph, show it to the operator, and revalidate the same plan inside the write transaction. It
identified `CompanyDataPurger.preview()` and `CompanyDataPurger.purge()` as the closest existing
repository pattern because they separate typed preview from guarded mutation.

The reviewer challenged owner-authorized lineage and recommended requiring an SEC filing that
explicitly binds both CIKs. The project owner kept the two-CIK, name-preview, `y/n` workflow.
The design therefore adopts the reviewer's mechanical safeguards but not its documentary-proof
requirement.

## Approaches Considered

- **CLI-first extension:** rejected because it would spread traversal and coverage logic across
  the existing SEC client, ingestion service, and evidence store.
- **Dedicated lineage domain:** selected because discovery, storage, mapping, and maintenance
  need one vocabulary and one deep interface.
- **Durable ingestion outbox:** deferred because queue claiming and crash recovery are excessive
  for the current sole-owner local workflow.

## Recommended Approach

Build a dedicated lineage domain and combined filing-window discovery, then make the maintenance
command a thin operator interface over it.

### Command contract

Add this package entry point:

```text
sec-inline-financials-lineage CURRENT_CIK PREDECESSOR_CIK
```

Example:

```text
$ uv run --no-sync sec-inline-financials-lineage 0002115436 0000034088

Current company
  ExxonMobil Holdings Corporation (CIK 0002115436)

Existing lineage
  0002115436  ExxonMobil Holdings Corporation

Proposed edge
  0000034088  Exxon Mobil Corporation
       ->
  0002115436  ExxonMobil Holdings Corporation

Create this lineage and ingest the predecessor's filings? [y/N]:
```

The argument order is always current CIK first, predecessor CIK second. Both accept padded or
unpadded decimal input and normalize to ten digits. Non-digits, zero, and values longer than ten
digits fail before SEC access.

The confirmation function reads one line:

- `y` or `Y`: apply the plan and start ingestion;
- `n`, `N`, blank, or EOF: print `Cancelled; no changes made.` and exit 0;
- `KeyboardInterrupt`: print the same cancellation message and exit 130;
- anything else: print `Please enter y or n.` and ask again.

There is no `--yes` or other noninteractive bypass in version one.

### Domain interfaces

Create `src/sec_inline_financials/company_lineage.py`:

```python
@dataclass(frozen=True)
class RegistrantIdentity:
    cik: str
    legal_name: str


@dataclass(frozen=True)
class LineageEdge:
    predecessor_cik: str
    successor_cik: str
    effective_date: date | None


@dataclass(frozen=True)
class CompanyLineage:
    company_id: int
    current: RegistrantIdentity
    registrants: tuple[RegistrantIdentity, ...]
    edges: tuple[LineageEdge, ...]
    lineage_hash: str

    def current_to_oldest(self) -> tuple[RegistrantIdentity, ...]: ...
    def unique_oldest(self) -> RegistrantIdentity: ...


@dataclass(frozen=True)
class LineagePatchPlan:
    company_id: int
    current_cik: str
    stored_current_name: str
    sec_current_name: str
    sec_predecessor_name: str
    predecessor: RegistrantIdentity
    successor: RegistrantIdentity
    before: CompanyLineage
    after: CompanyLineage
    expected_lineage_hash: str
    already_applied: bool
```

`LineagePatchPlan` is the object displayed to the operator and later applied. Its lineage hash is
SHA-256 over canonical JSON containing the normalized current CIK, ordered active memberships,
and ordered edges with nullable effective dates. Mutable legal names and database row IDs are
excluded. The store recomputes the hash after acquiring the SQLite write lock. A mismatch aborts
with a clear conflict instead of applying a stale preview.

Create `src/sec_inline_financials/lineage_maintenance.py`:

```python
class LineageMaintenanceService:
    def preview_link(
        self,
        current_cik: str,
        predecessor_cik: str,
    ) -> LineagePatchPlan: ...

    def apply_link(self, plan: LineagePatchPlan) -> AppliedLineageChange: ...

    def apply_and_ingest(
        self,
        plan: LineagePatchPlan,
        *,
        progress: ProgressCallback | None = None,
    ) -> LineageMaintenanceResult: ...
```

`preview_link()` performs only reads and SEC legal-name resolution. `apply_link()` revalidates
and commits only the lineage. `apply_and_ingest()` calls `apply_link()` and then invokes the
ordinary company-ingestion service with a forced refresh. It does not implement a predecessor-
specific evidence pipeline.

Extend `SecClient` with:

```python
def resolve_registrant(self, cik: str) -> RegistrantIdentity: ...

def discover_company_window(
    self,
    company: Company,
    lineage: CompanyLineage,
    *,
    annual_count: int,
    quarterly_count: int,
) -> DiscoveredCompanyWindow: ...
```

`resolve_registrant()` reads `data.sec.gov/submissions/CIK{cik}.json`, normalizes the response's
top-level CIK, and requires it to equal the normalized CIK requested by the operator. It also
requires a nonblank top-level SEC name. A mismatch or missing name raises `DiscoveryError` before
preview, confirmation, or any write. The method does not search for or prove a relationship. The
preview models the stored current-company name and freshly resolved SEC name separately and
displays both when they differ. Applying a lineage patch preserves `companies.current_name`; it
inserts or refreshes only the registrant display name in the lineage tables.

`discover_company_window()` owns current-to-oldest traversal, submissions history pagination,
exact-form Inline XBRL filtering, annual report-year selection, quarterly report-date selection,
global accession deduplication, archive ownership, and per-form coverage. It stops fetching
older registrants once both source-priority windows have their requested number of positions.

### Storage migration

Add, do not rewrite, `src/sec_inline_financials/storage/sql/0007_cik_lineage.sql`.

The DDL-level contract is:

```text

  legal_name TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
)

company_ciks(
  company_id INTEGER NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  cik TEXT NOT NULL REFERENCES registrants(cik) ON DELETE RESTRICT,

  is_active INTEGER NOT NULL CHECK(is_active IN (0, 1)),

  requested_count INTEGER NOT NULL CHECK(requested_count > 0),
  discovered_count INTEGER NOT NULL CHECK(discovered_count >= 0),
  usable_count INTEGER NOT NULL CHECK(usable_count >= 0),

  slot_key TEXT NOT NULL,

  UNIQUE(publication_id, slot_key),
  UNIQUE(publication_id, selection_rank),
  FOREIGN KEY(snapshot_id, filing_id) REFERENCES evidence_snapshots(id, filing_id)

active_window_heads(
  company_id INTEGER NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  form TEXT NOT NULL CHECK(form IN ('10-K', '10-Q')),
  publication_id INTEGER NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY(company_id, form),
  FOREIGN KEY(publication_id, company_id, form)
    REFERENCES active_window_publications(id, company_id, form)

```

Required indexes are:

- a partial unique index on `company_ciks(company_id)` where `is_active = 1 AND
  is_current = 1`, enforcing one active current member;
- partial unique indexes on `(company_id, predecessor_cik)` and
  `(company_id, successor_cik)` where the transition is active, preventing branches and
  merges;
- lookup indexes on active memberships and transitions by `company_id`;
- `filing_provenance(registrant_cik, filing_id)`; and
- `active_window_publications(company_id, form, created_at)` plus
  `active_window_memberships(publication_id, selection_rank)`.

The composite snapshot foreign key relies on the existing
`evidence_snapshots UNIQUE(id, filing_id)` constraint from migration 0001; migration tests assert
that exact parent key exists before applying migration 0007. Application validation requires
`usable_count` to equal the membership count and to be no greater than either
`discovered_count` or `requested_count` before a publication can commit.

Version one deliberately stores one primary registrant per filing. Multi-registrant joint
filings are deferred until a supported fixture requires them. Archive owner and discovery
origin remain separate fields.

The lineage hash identifies an immutable graph state, not a filing. A graph change inserts a
`company_lineage_versions` row in the same transaction as the membership and edge mutation.
Immutable filing-origin provenance never changes when a later graph version selects that filing;
the active-window publication references the graph version instead.

Version-6 backfill inserts every legacy `companies.cik/current_name` into `registrants`, creates
one active current `company_ciks` membership, inserts its singleton lineage version, and records
each legacy filing's registrant, archive owner, and discovery origin as that existing company
CIK. This is valid because the version-6 client built every legacy URL from `companies.cik`.
Existing `filings.is_active` and `active_filing_snapshots` remain readable as legacy state; the
first lineage-aware refresh creates a versioned publication and updates the compatibility
projection. Existing snapshot and artifact bytes remain unchanged.

After migration, every normal company creation transaction must also insert its registrant,
current membership, and singleton lineage version. Every ordinary filing upsert must atomically
insert singular filing provenance. Tests cover a new single-CIK company and its first filing
after migration so the model cannot drift immediately after backfill.

Migration tests run against a copied version-6 database and require both
`PRAGMA foreign_key_check` and `PRAGMA integrity_check` to pass.

Company purge deletes filings and their provenance, then the company deletion cascades through
memberships, transitions, graph versions, publications, memberships, and heads. It finally
deletes any now-unreferenced global registrant rows. Tests execute the real SQLite purge order so
endpoint cascades cannot block deletion.

Do not store authorization source, confirmer identity, prompt response, or a fabricated
effective date. Normal `created_at` and `updated_at` columns remain ordinary database lifecycle
fields.

### Transactional preview and apply

`EvidenceStore.preview_lineage_patch(current_cik, predecessor)`:

1. requires exactly one canonical company whose current membership matches `current_cik`;
2. loads the ordered lineage and finds its unique oldest member;
3. rejects a predecessor already owned by another canonical company;
4. returns an idempotent no-op when the same membership and edge are already active, or a
   reactivation plan when that exact reserved membership and edge are inactive;
5. rejects incompatible existing edges, multiple oldest members, cycles, and self-links; and
6. returns a `LineagePatchPlan` containing the complete before/after graph and state hash.

`EvidenceStore.apply_lineage_patch(plan)` starts `BEGIN IMMEDIATE`, then reloads the graph,
recomputes the hash, and repeats every invariant. A new relationship inserts its registrant,
membership, edge, and lineage-version row. If the exact membership and transition exist but are
inactive after an earlier unlink, the same rows are reactivated atomically, the registrant legal
name is refreshed, and the already-existing immutable lineage-version row is reused. A repeated
link to an active edge returns `already_present`. Acquiring the write lock before the validation
read serializes competing writers. Any other uniqueness or state conflict raises
`StaleLineagePlan` or `LineageConflict`. It performs no SEC request and no Arelle work while
holding the transaction. Link, unlink, relink, and repeated relink therefore converge without
duplicate memberships, transitions, or graph versions.

### Ingestion flow

After the edge commits:

1. call a new internal `CompanyIngestionService.ingest_company_id(company_id, force=True)`
   entry point using the exact stored company and lineage; ticker remains display metadata;
2. resolve the now-stored lineage;
3. call `discover_company_window()` once for both report kinds;
4. normalize each `DiscoveredFiling` into the unchanged core `Filing` plus sidecar registrant
   and archive-owner provenance;
5. send each accession without a reusable completed snapshot through the ordinary
   `EvidenceIngestionService` and Arelle processor;
6. persist annual and quarterly coverage independently;
7. compare and publish candidate windows independently by form using the monotonic rule below;
   and
8. run Direct Mapping independently for each non-empty form over successfully snapshot-backed
   filings.

The maintenance command prints the committed relationship before starting ingestion. If the
process stops after that point, rerunning produces an `already_present` plan and resumes the
same ordinary ingestion path.

`CompanyIngestionService.ingest_company_id()` and the public ticker entry point both delegate to
one internal `ingest_resolved_company(company, lineage, ...)` implementation. The maintenance
path never resolves the ticker again, avoiding stale or changed ticker bindings during a legal
succession.

There are no resumable sub-filing stages in version one. A filing is reusable only when a
completed immutable snapshot with the same source-manifest and extraction-profile hashes exists
and the required classification/section coverage is present. Metadata without such a snapshot,
or a latest processing-attempt state of `pending`, stale `processing`, `failed`, or
`interrupted`, reruns the entire filing pipeline. Content-addressed artifacts may be reused.
Direct Mapping is a separate idempotent stage and reruns from the selected active snapshots.

If fetching one registrant's submissions or history fails, traversal stops at that member;
lower-priority members are not used because priority across the gap cannot be proven. Filings
already discovered from higher-priority members may still be processed and may publish an
improved partial window, but coverage records `had_fetch_error = 1`, the command exits nonzero,
and an existing better window is preserved. A current-member fetch failure therefore retains
the previous publication and processes no lower-priority member.

### Filing selection and retrieval

For annual filings, the exact slot key is `Y:{report_date.year:04d}`. This is intentionally a
report-year key derived from SEC submissions `reportDate`, not a claim about a separately parsed
fiscal year. For quarterly filings, the exact slot key is `D:{report_date.isoformat()}`.

Only exact `10-K` and `10-Q` forms with Inline XBRL eligibility enter the candidate set;
amendments such as `10-K/A` and `10-Q/A` do not. An otherwise eligible row with a missing or
invalid `reportDate` or `filingDate` is a registrant metadata error: discovery stops at that
member, records the error for the affected form, and returns a nonzero command outcome instead
of silently skipping the row. Within one registrant and slot, choose the candidate with the
greatest `(filing_date, accession)` tuple. The accession is the stable final tie-breaker.
Transition filings with an exact supported form follow the same rule.

Selection then proceeds one registrant at a time, current to oldest:

1. deduplicate one registrant's eligible rows within each slot;
2. sort the surviving annual slot keys by report year descending and quarterly slot keys by ISO
   report date descending;
3. add the current CIK's newest slots to unfilled positions, up to the requested count;
4. deduplicate globally by accession;
5. fetch the next predecessor only while either report kind is short;
6. add that predecessor's newest filings only to still-empty slots; and
7. stop when requested counts are complete or the stored lineage is exhausted.

This is explicitly a **source-priority window**, not a claim that the result is the globally
latest set across every lineage member. If both CIKs contain an eligible filing for the same
slot, the current-first selection remains authoritative. A request for one exact slot applies
the same current-to-oldest lookup. The selected filing retains its primary registrant CIK and
archive-owner CIK.

### Active-window publication rule

For each form, let `R` be the requested count, `D` the number of deterministic selected slots
before filing processing, `U` the number of those slots with reusable or newly successful
snapshots, `F` whether submissions/history transport failed, `M` whether otherwise eligible SEC
metadata was invalid, and `P` the count of selected filings that failed or were interrupted.
Every outcome must satisfy `0 <= U <= D <= R`. Coverage is assigned by this exhaustive table:

| Condition | `coverage_status` | Command interpretation |
|---|---|---|
| `U = R`, `F = M = 0`, `P = 0` | `complete` | requested form window is usable |
| `0 < U < R` | `partial` | history shortfall if error flags are clear; otherwise retryable partial |
| `U = 0`, `F = M = 0`, `P = 0` | `empty` | no usable filing and no operational failure |
| `U = 0` and any of `F`, `M`, or `P > 0` | `error` | retryable discovery or processing failure |

States outside the table, including `U = R` with an error flag or `U > D`, are invariant
violations and cannot publish. `D`, `F`, `M`, `P`, and detailed failure diagnostics remain audit
data; they never make one candidate preferable to another.

Each candidate form window persists its comparison inputs. The monotonic comparison tuple uses
only successfully usable evidence:

```text
(
  completeness_rank,          # U=R: 2, 0<U<R: 1, U=0: 0
  usable_snapshot_count,
  ordered_usable_slot_keys_desc,
  ordered_usable_(filing_date, accession)_desc
)
```

A candidate replaces the current form head only when this tuple is lexicographically greater,
or when it is byte-for-byte equivalent and therefore an idempotent no-op. This prevents a
partial refresh from replacing a complete window, prefers more usable evidence, and advances a
same-size complete window only when its ordered periods or filings are newer. Annual and
quarterly heads compare independently. A candidate carrying fetch, metadata, or processing
errors may publish a usable partial subset only when that usable-evidence tuple is strictly
greater than the current head; discovery volume and failures themselves cannot improve its rank.
An outcome with `U = 0` is retained for diagnostics but never installed as an active head.

The publication, memberships, head update, legacy `filings.is_active` projection, and legacy
`active_filing_snapshots` projection commit in one transaction. Direct Mapping reads the
versioned head and includes its lineage hash, filing registrant CIK, and archive-owner CIK in the
active-window fingerprint.

Online retrieval reads the published local active window and its snapshots. It does not repeat
lineage traversal against the SEC. Historical raw facts and XBRL context entity identifiers
remain exactly as filed.

Direct Mapping compares each context entity identifier with that filing's primary registrant
CIK, not
the canonical current CIK. The active-window fingerprint includes registrant and archive-owner
identity so pre-lineage evaluations are not reused incorrectly.

### CLI result and exit semantics

`LineageMaintenanceResult` contains `relationship_status` (`created`, `reactivated`, or
`already_present`), separate annual and quarterly `FormOutcome` values, the ingestion run ID,
published publication IDs, warnings, and a final status:

- `complete`: both requested form windows are complete and every attempted selected filing was
  stored or reused;
- `partial_history`: at least one form has usable evidence, no fetch or processing attempt
  failed and no eligible-row metadata was invalid, but one or both forms are short or empty
  because eligible history does not exist;
- `partial_processing_failure`: usable evidence exists, but at least one selected filing failed
  or was interrupted;
- `empty`: neither form produced a usable snapshot;
- `fetch_failed`: a required current or predecessor submissions/history request failed; and
- `metadata_invalid`: an otherwise eligible SEC submissions row had an invalid required date;
  and
- `cancelled`: the operator did not approve the change.

When form outcomes differ, the aggregate status uses this deterministic precedence:
`metadata_invalid`, `fetch_failed`, `partial_processing_failure`, `empty`, `partial_history`, then
`complete`. `empty` applies only when neither form has usable evidence and no higher-precedence
failure exists; one usable form plus a clean empty or short form is `partial_history`.

| Condition | Database result | Ingestion | Exit |
|---|---|---|---|
| invalid CIK or current CIK absent | unchanged | not started | 1 |
| SEC legal-name resolution fails | unchanged | not started | 1 |
| cycle, cross-company ownership, or ambiguous graph | unchanged | not started | 1 |
| operator answers no/blank/EOF | unchanged | not started | 0 |
| operator interrupts | unchanged | not started | 130 |
| identical edge already exists and operator answers yes | unchanged/no-op | retried | ingestion result |
| `complete` | relationship retained | complete | 0 |
| `partial_history`, including one empty form | relationship retained | usable warning | 0 |
| `partial_processing_failure` | relationship and valid evidence retained | retryable warning | 1 |
| `empty` | relationship retained | no usable evidence | 1 |
| `fetch_failed` | relationship and any earlier valid evidence retained | retryable failure | 1 |
| `metadata_invalid` | relationship and any earlier valid evidence retained | retryable failure | 1 |

Any selected-filing processing failure makes the command nonzero even when a partial window was
published. A count shortfall with no transport, metadata, or processing failure is
`partial_history` and exits zero. Every nonzero post-commit message must say that the relationship
was retained and print the exact rerun command; it must not imply that the entire operation rolled
back.

### Safe correction path

Persistent rollout includes a separate two-argument command:

```text
sec-inline-financials-lineage-unlink CURRENT_CIK PREDECESSOR_CIK
```

It uses the same legal-name lookup, before/after graph rendering, `y/n` confirmation, state-hash
check, and `BEGIN IMMEDIATE` revalidation. Version one can deactivate only the active oldest
source member and its single outgoing edge; it refuses arbitrary middle-of-chain surgery or any
unlink that would create a disconnected active graph.

The unlink transaction marks that edge and membership inactive, inserts or reuses the resulting
immutable lineage version, deletes every versioned active-window head for the company, sets
`filings.is_active = 0` and `filings.active_window_rank = NULL` for the company, and deletes from
`active_filing_snapshots` where `filing_id` belongs to that company, all in the same transaction.
It never deletes
filings, snapshots, raw facts, artifacts, publications, or immutable filing provenance. After
commit it runs a forced `company_id` refresh over the remaining active chain. If refresh fails,
neither versioned retrieval nor the legacy compatibility projection exposes a stale predecessor-
backed window; retained evidence remains inspectable, and rerunning the refresh is safe. The
inactive membership continues reserving the CIK to the same canonical company; moving it
elsewhere requires a separate explicit reconciliation design.

An approved unlink returns relationship status `removed` when it deactivates the active oldest
edge and `already_absent` when that exact edge is already inactive. Both statuses run the forced
refresh: `already_absent` is an idempotent retry, not a reason to leave a prior failed refresh
unfinished. Successful refresh or a history-only shortfall exits 0; any discovery, metadata, or
processing failure exits 1; cancellation exits 0; interruption exits 130. A later link of the
same pair reactivates the reserved membership and transition as described above.
