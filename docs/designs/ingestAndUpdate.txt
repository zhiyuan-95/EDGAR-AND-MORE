# SEC Inline Financials: Ingestion and Update Design

**Status:** Implemented for durable evidence ingestion and active-window refresh
**Scope:** Current `sec_inline_financials` repository only
**Out of scope:** Metric mapping, LLM recommendations, frontend delivery, and scheduled jobs

## 1. Public entry points

The primary console command is:

```powershell
uv run --no-sync sec-inline-financials AAPL
uv run --no-sync sec-inline-financials AAPL MSFT NVDA
uv run --no-sync sec-inline-financials AAPL,MSFT,NVDA
```

It runs the production company-ingestion path for one or more tickers, writes
flushed progress to stderr, then writes each company/run summary, elapsed time,
and resolved evidence paths to stdout. Multi-company ingestion is sequential; if
one ticker fails, the command reports that error, continues with the remaining
tickers, and exits nonzero after the batch finishes.

The lower-level console aliases run the same ingestion without the final timing and
path lines:

```powershell
uv run --no-sync sec-inline-financials-ingest AAPL
uv run --no-sync sec-inline-financials-ingest AAPL MSFT NVDA
uv run --no-sync python -m sec_inline_financials.company_ingestion AAPL
```

The public Python entry point is:

```text
ingest_company(ticker, settings, progress=None)
    -> CompanyIngestionResult
```

The wrapper does not silently authorize upgrades to an existing evidence database.
An embedding application that accepts a pending schema upgrade must first initialize
the same database with `EvidenceStore.initialize(allow_schema_upgrade=True)`; a
normal `initialize()` or `ingest_company(...)` call refuses a pending upgrade.

Supported settings include `annual_count`, `quarterly_count`, `force_refresh`, the
SQLite path, artifact root, SEC User-Agent, and Arelle cache directory. The CLI
defaults to five exact-form Inline XBRL 10-K filings and twelve exact-form Inline
XBRL 10-Q filings. `--force` requests an SEC check even when stored next-check dates
are in the future.

No next-check date starts work by itself. Ingestion is always request-triggered.

## 2. Runtime storage

`SEC_INLINE_FINANCIALS_DATA_DIR` controls the evidence root. When it is unset, the
default is:

```text
%LOCALAPPDATA%/SECInlineFinancials/data/
  evidence.sqlite3
  objects/sha256/<first-two-hash-characters>/<full-sha256>
  staging/<attempt-id>/
  cache/arelle/
```

SQLite is the structured source of truth. The object directory contains immutable,
content-addressed source documents, Arelle logs, and source manifests. Live data
belongs outside the source checkout.

## 3. Request decision sequence

`CompanyIngestionService.ingest_company` executes this decision sequence:

1. Normalize and validate the ticker and filing counts.
2. Initialize the evidence store with packaged, checksum-verified migrations. A new
   database initializes automatically. An existing database with pending migrations
   proceeds only after the CLI lists them and receives explicit operator approval;
   the service/API refuses the upgrade unless its caller has applied it explicitly.
3. Read stored company state, active accessions, snapshot coverage, narrative-section
   coverage, and next-check dates.
4. Contact the SEC only when at least one condition is true:
   - the caller used `--force`;
   - the company has no usable stored evidence;
   - an active filing has no evidence snapshot;
   - an active filing has no current narrative-section snapshot; or
   - an annual or quarterly next-check date is due.
5. If none is true, return `reused_local` without constructing the SEC client or
   Arelle processor.

An active legacy `evidence-v1` window has no `filing_sections`. Its next request is
therefore treated as incomplete even when the next-check dates are in the future.
The request performs SEC discovery and creates `evidence-v3` snapshots instead of
mutating the legacy snapshots.

## 4. SEC discovery

When a refresh is required:

1. Resolve the ticker to the current SEC company and CIK.
2. Reject a stored ticker/current-CIK ownership conflict.
3. Load the operator-verified registrant lineage from storage, or use an in-memory
   singleton containing only the current CIK when no lineage has been stored.
4. Read recent and archived SEC submissions metadata for the lineage from current
   registrant toward older predecessors. Higher-priority registrants keep an annual
   year or quarterly report-date slot; an older predecessor fills gaps only.
5. Select both the requested annual and quarterly windows. A due check for one form
   still enters the shared discovery path for both forms.
6. Annual selection keeps eligible `isInlineXBRL = true` exact-form `10-K` filings,
   groups candidates by report-date year, and keeps the latest filed candidate for
   each selected year.
7. Quarterly selection keeps the latest eligible `isInlineXBRL = true` exact-form
   `10-Q` filings.

Lineage is never inferred from names, tickers, accession prefixes, or `formerNames`.
Each selected filing preserves its registrant CIK and SEC archive-owner CIK in
`filing_provenance`. A selected current-registrant filing that later fails processing
is not replaced by a predecessor filing for the same slot.

The requested counts are upper bounds, not a completeness gate. If SEC history has
fewer eligible filings than requested for either form, discovery returns every
eligible filing it found. The shortage is reported as a coverage warning and does
not count as an ingestion failure. Each found filing still continues through Arelle,
evidence storage, classification, and Direct Mapping. Annual and quarterly mapping
are evaluated independently, so an empty form does not prevent mapping the other
non-empty form. No placeholder filing or period is created for missing history.

`10-K/A` and `10-Q/A` do not consume window positions because discovery requests
exact forms. SEC submissions provide identity and filing URLs; financial values come
from the filing-scoped Arelle models, not the SEC Company Facts API.

If SEC access or metadata parsing raises `DiscoveryError` and no usable evidence
exists, the error propagates. A count shortage by itself does not raise
`DiscoveryError`. If usable evidence already exists, return
`refresh_failed_using_local_data` and keep the published local window unchanged.

## 5. Per-filing Arelle processing

`EvidenceIngestionService` deduplicates the selected accessions and processes them
sequentially. Each filing receives its own processing-attempt record.

For each filing:

1. Build the extraction profile from the application version, extractor and
   serialization versions, installed Arelle version, validation options, and pinned
   SEC transformation-plugin hashes.
2. Look for a snapshot with the same accession and extraction-profile hash.
3. If found, verify every linked artifact's path, byte size, and SHA-256. Recreate a
   missing `report-v2` evaluation from stored evidence when necessary, then mark the
   attempt `reused` without SEC/Arelle processing.
4. Otherwise create an attempt-private staging directory and Arelle cache.
5. Open the filing URL with Arelle in online mode using the configured SEC User-Agent.
   Validation is enabled with Calculation 1.0 deduplication (`c10d`), duplicate-fact
   validation, warning-level buffered logs, the pinned SEC transformation plugin,
   and the local SEC extension-taxonomy retry plugin. The retry applies only to an
   HTTP 503 for an HTTPS `.xsd` URL below `sec.gov/Archives/edgar/data/` or
   `www.sec.gov/Archives/edgar/data/`; it makes three additional attempts after
   1, 2, and 4 seconds. Other failures propagate without this retry.
6. Before the Arelle session closes, capture the raw log and detach all exposed
   recognized and undefined observations, concepts, labels, contexts, units,
   dimensions, diagnostics, validation records, and supported calculation networks.
7. Capture the exact primary Inline document plus loaded filing-owned Inline,
   schema, and linkbase resources. External dependencies may remain recorded
   references rather than archived files.
8. Parse the retained primary document into required narrative-section records.
9. Close Arelle, classify every observation under `report-v2`, install immutable
   artifacts, and save the snapshot.

The current `evidence-v3` section set is:

- 10-K: Items 1, 1A, 3, 7, 7A, and 8.
- 10-Q: Part I Items 1, 2, 3, and 4; Part II Items 1 and 1A.

Each required section records its status (`extracted`, `not_found`, or
`parse_error`), ordered identity, source-document link, source range, normalized
text, content hash when extracted, and diagnostic when unavailable. Missing or
unparseable content is not stored as an empty disclosure.

## 6. Snapshot and artifact storage

Artifacts are installed before the database snapshot transaction. Each object is
named by its SHA-256 and is never overwritten with different bytes. Recoverable
unreferenced objects may remain if a process stops between object installation and
the SQLite commit.

`EvidenceStore.save_snapshot` validates the bundle and then uses one short
`BEGIN IMMEDIATE` transaction to:

1. register the company, filing, artifacts, and attempt links;
2. recheck the snapshot identity;
3. insert one immutable evidence snapshot when no identical snapshot exists;
4. insert source documents and narrative sections;
5. insert concepts, labels, contexts, dimensions, units, every fact occurrence,
   diagnostics, validation messages/references, roles, networks, and calculation
   arcs;
6. insert the versioned report evaluation and fact roles/exclusion reasons; and
7. mark the attempt `stored`.

A repeated snapshot identity with a different semantic payload is an integrity
error, not an update. A newer extraction profile creates another snapshot for the
same accession. Older snapshots remain queryable.

After a confirmed store/reuse result, the successful attempt's staging directory is
removed. A failed filing is marked separately and cannot expose a partial snapshot.
Earlier completed filings remain usable.

## 7. Run completion and active-window publication

A processing run is:

- `succeeded` when every attempt stored or reused a snapshot;
- `partial` when at least one attempt succeeded/reused and at least one failed; or
- `failed` when no attempt succeeded or reused evidence.

For an initial company, a fully failed run raises `IngestionError`. A partial initial
run can publish usable filings; failed active filings remain visibly incomplete and
force a later retry. For a stored company, a fully failed processing run returns the
local-data fallback.

After a usable run, one transaction publishes the selected filing window:

1. upsert selected filing metadata;
2. mark the company's older filing rows inactive without deleting their snapshots;
3. assign annual and quarterly active-window ranks;
4. update latest filing dates; and
5. update annual and quarterly next-check dates.

The active window controls current selection, not evidence retention. Historical
filing rows, snapshots, observations, sections, and artifact links remain stored.

## 8. Refresh-date policy

A check is due when its date is missing or today is on/after the stored date.

After initial evidence or a new selected accession:

- 10-K: latest selected filing date plus 12 months.
- Q1/Q2 10-Q: latest selected filing date plus 3 months.
- Q3 10-Q: latest selected filing date plus 6 months.

The calculated date moves backward to the preceding supported market day. A due
check with no new selected accession moves that form's next check to the next
supported market day after today. A failed attempt for a form makes that form due
again immediately. These dates are polling heuristics, not guaranteed filing dates.

## 9. Result statuses

`initialized`
The company had no usable evidence before this request and the run produced usable
evidence.

`updated`
SEC discovery selected at least one accession not previously known to the store.

`checked_no_update`
SEC was checked, but no newly selected accession was found. The run may still have
created newer-profile snapshots, such as the `evidence-v3` section backfill.

`checked_no_filings`
SEC and every stored lineage member were checked, but neither form produced an
eligible filing. No placeholder filing, snapshot, period, or mapping result is
created.

`reused_local`
The local active window was complete and current, so SEC and Arelle were skipped.

`refresh_failed_using_local_data`
SEC discovery or filing processing failed for a company with usable stored evidence;
the last published window remains available.

These statuses describe the request outcome. They are not database insert counts.
Per-filing outcomes remain available on `result.run` when a processing run occurred.

## 10. Progress, output, and concurrency

Progress callbacks cover initialization, local-state checks, SEC discovery,
selection, every filing start/finish, active-window publication, and completion.
The CLI writes these messages to stderr with `flush=True`. Final result summaries
stay on stdout.

`sec-inline-financials` also prints elapsed time and the resolved evidence root,
content-addressed object directory, and SQLite path after the ingestion command
returns. `sec-inline-financials-ingest` and the module entry point omit those extra
lines. All forms accept multiple tickers separated by spaces or commas.

Selected filings run sequentially. Arelle sessions share process state and must not
be run concurrently in threads.

## 11. Recovery, backup, and integrity boundaries

`recover_interrupted_attempts(store)` is available to mark attempts whose owner
process is no longer alive. The current production CLI does not invoke it
automatically, so operators should call it explicitly before manual recovery work.
It does not delete staging directories, committed artifacts, or immutable objects.

`audit_snapshot` verifies row/link counts, referenced artifact hashes and sizes, and
SQLite foreign keys. `resolve_artifact` verifies an object again before returning its
path. Missing or changed bytes are explicit integrity failures; evidence rows remain
for diagnosis.

Backup uses SQLite's backup interface plus every referenced immutable artifact and a
hash manifest. Do not copy only an open `evidence.sqlite3` file because committed WAL
state may be outside the main file.

## 12. Report, mapping, and frontend boundaries

Ingestion never renders or writes TXT reports. Reports are generated only from
stored snapshots through:

```text
uv run --no-sync python tests/inspect_inline_ingestion.py
```

The script prompts for the ticker, report type, and fiscal years, then writes a TXT
report plus a complete-facts JSON export. The two ingestion console scripts do not
generate reports; `sec-inline-financials-map` evaluates only stored evidence.

Direct Mapping and metric-result persistence are implemented by the separate
Milestone 2 components. After a successful active-window publication, ingestion
evaluates or reuses mapping in a separate failure boundary; mapping failure cannot
roll back evidence or change the ingestion status. LLM evidence
packets/recommendations, human review, API endpoints, evidence downloads, and the
browser frontend remain planned. Ingestion does not synchronize a retrieval index.

## 13. Verification boundary

The active offline suite covers evidence storage and migrations, ingestion and
partial filing windows, CIK lineage maintenance and provenance, report-v2 transition
classification, Direct Mapping and batched registrant lookup, narrative-section
extraction/replay, lossless text-payload compaction and purge cleanup, and the scoped
SEC taxonomy retry. Historical production CLI runs separately recorded full 5/12
evidence-v2 windows and artifact audits. The current checkout has no opt-in live
pytest, and a live update that discovers a genuinely new accession remains a
separate acceptance case.
