# Milestone 2 Direct Mapping Implementation Plan

Status: Implemented 2026-09-15
Scope: Backend-only Direct Mapping for the seven Target Metrics
Depends on: Existing evidence-v2 snapshots and persisted report-v1 decisions

## 1. Naming decision

Before this implementation, the documentation used two milestone-numbering schemes:

- README.md calls Direct Mapping the next Milestone 2.
- docs/designs/project_proposal.txt calls incremental evidence updates Milestone 2
  and Direct Mapping Milestone 3.

The blueprint now groups durable storage and incremental evidence updates under
Milestone 1 and consistently names Direct Mapping as Milestone 2. Code, database
versions, and interfaces use the feature name "Direct Mapping" rather than
depending on a milestone number.

## 2. Outcome

Implement deterministic Direct Mapping over evidence already stored in SQLite.
For every active annual and quarterly filing period, evaluate all seven Target
Metrics and persist either a reported fact or an explicit missing result.

The seven Target Metrics are:

1. Revenue
2. Operating Income
3. Net Income
4. Total Assets
5. Total Liabilities
6. Equity
7. Operating Cash Flow

For the normal complete company window, one evaluation produces 119 results:

    7 metrics * (5 annual filings + 12 quarterly filings) = 119 results

The completed milestone must:

- evaluate mappings independently for each exact annual or quarterly period;
- keep annual and quarterly concept populations separate;
- apply configured primary and alternative concepts in deterministic order;
- preserve a reported numeric zero as a reported result;
- store one result for every Target Metric and supported filing period;
- link every reported result to its exact stored fact, snapshot, filing, and
  report-v1 evaluation;
- retain explicit missing results for the later Mapping Recommendation workflow;
- reuse an existing evaluation when its evidence window and rule versions have not
  changed; and
- run entirely from stored evidence without SEC access, Arelle processing, LLM
  calls, or report generation.

## 3. Non-goals

This milestone does not implement:

- LLM candidate discovery or Mapping Recommendations;
- approval or rejection of recommended mappings;
- company-specific accepted mapping overrides;
- composite or derived metrics;
- Q4 derivation from annual and nine-month facts;
- year-to-date subtraction for quarterly cash-flow values;
- frontend pages or local HTTP endpoints;
- changes to Arelle extraction; or
- automatic TXT or JSON report generation.

## 4. Current-system seams

Direct Mapping should build on the current implementation rather than introduce a
parallel data path.

### 4.1 Existing evidence source

The normalized evidence store already contains:

- companies and filings;
- immutable evidence snapshots and payload hashes;
- concepts identified by namespace URI and local name;
- contexts with entity and exact period data;
- units and unit measures;
- exact fact occurrences and typed numeric text;
- dimensions linked through contexts;
- validation evidence and extraction diagnostics;
- report-v1 classifications and exclusion reasons; and
- reconciliation issues and their candidate facts.

Direct Mapping must read these normalized records. It must not parse generated TXT
reports or complete-facts JSON exports.

### 4.2 Existing report-v1 decisions

report-v1 already classifies every stored observation as one of:

- selected_primary;
- dimensional;
- duplicate_not_selected;
- conflict_candidate; or
- excluded.

Direct Mapping should consume selected_primary facts and retain the other roles and
exclusion codes as diagnostic evidence. It should not duplicate report-v1 numeric,
nil, validity, period-end, duration, dimension, duplicate, or conflict selection
logic.

### 4.3 Existing EvidenceStore module

EvidenceStore currently owns SQLite configuration, transactions, snapshot storage,
report-evaluation storage, bounded fact retrieval, artifact integrity checks, and
active filing-window publication.

Keep EvidenceStore as the storage module. Add focused mapping methods to it instead
of creating a second SQL repository layer or embedding SQL in the mapping resolver.

### 4.4 Gaps addressed by this milestone

The implementation fills two structural gaps:

1. Active filings currently have is_active and active_window_rank, but no explicit
   pointer to the exact immutable snapshot downstream products should consume.
2. There is no versioned mapping-rule model, metric-evaluation schema, resolver, or
   published metric-evaluation pointer.

At plan authoring time, pytest collected zero tests. The implementation adds
automated resolver, rules, storage, service, CLI, and ingestion-integration coverage,
including a complete synthetic 5/12 window and stored-evidence AAPL acceptance.

## 5. Implemented module structure

The runtime flow is:

    checked-in direct-mapping-v1 rules
                    |
                    v
    active 10-K and 10-Q filing windows
                    |
                    v
    exact published filing/snapshot bindings
                    |
                    v
    persisted report-v1 decisions
                    |
                    v
    bounded annual and quarterly candidate queries
                    |
                    v
    deterministic Direct Mapping resolver
                    |
           +--------+--------+
           |                 |
           v                 v
    reported result     missing result
    plus fact link      plus resolution trace
           |                 |
           +--------+--------+
                    |
                    v
    immutable evaluation and published pointer

Create these modules:

    src/sec_inline_financials/mapping_models.py
    src/sec_inline_financials/mapping_rules.py
    src/sec_inline_financials/direct_mapping.py
    src/sec_inline_financials/mapping_service.py

The main application interface should remain small:

    DirectMappingService.evaluate_company(
        ticker: str,
        *,
        require_complete_window: bool = True,
    ) -> CompanyMappingResult

The deterministic resolver can expose a pure interface:

    resolve_metric_window(
        rule_set: DirectMappingRuleSet,
        report_kind: ReportKind,
        snapshots: tuple[MappingSnapshotInput, ...],
        observed_concepts: frozenset[ConceptIdentity],
        selectable_facts: tuple[MappingFactInput, ...],
    ) -> MetricWindowEvaluation

The service owns input selection, reuse, persistence, and publication. The resolver
must not open SQLite, access the filesystem, contact the SEC, open Arelle, call an
LLM, or render a report.

Do not introduce a storage port solely for testing. Temporary SQLite databases are
the existing local test adapter for EvidenceStore.

## 6. Versioned mapping rules

### 6.1 Runtime source

Do not parse root mapping.txt on every request. That file is not guaranteed to be
present in an installed wheel and its numbered prose format is not a stable runtime
interface.

Create frozen typed rule objects in mapping_rules.py with these constants:

    DIRECT_MAPPING_RULE_VERSION = "direct-mapping-v1"
    TARGET_METRIC_DEFINITION_VERSION = "target-metrics-v1"

Each MetricRule contains:

- metric_key;
- display_name;
- expected_period_type: duration or instant;
- expected_unit_family: monetary; and
- an ordered tuple of ConceptCandidate objects.

Each ConceptCandidate contains:

- namespace_family;
- local_name; and
- rank, beginning with zero for the primary concept.

Serialize the full ordered rule set to canonical JSON and calculate its SHA-256.
Store both values on every metric evaluation. Changing rule content requires a new
rule version; changing content under an existing version is an error.

### 6.2 Initial rules

Revenue
  Period type: duration
  0. us-gaap:RevenueFromContractWithCustomerExcludingAssessedTax
  1. us-gaap:Revenues
  2. us-gaap:SalesRevenueNet
  3. us-gaap:RevenueFromContractWithCustomerIncludingAssessedTax

Operating Income
  Period type: duration
  0. us-gaap:OperatingIncomeLoss

Net Income
  Period type: duration
  0. us-gaap:NetIncomeLoss
  1. us-gaap:ProfitLoss

Total Assets
  Period type: instant
  0. us-gaap:Assets

Total Liabilities
  Period type: instant
  0. us-gaap:Liabilities

Equity
  Period type: instant
  0. us-gaap:StockholdersEquity
  1. us-gaap:StockholdersEquityIncludingPortionAttributableToNoncontrollingInterest

Operating Cash Flow
  Period type: duration
  0. us-gaap:NetCashProvidedByUsedInOperatingActivities
  1. us-gaap:NetCashProvidedByUsedInOperatingActivitiesContinuingOperations

All initial concepts belong to the us-gaap namespace family. Matching must verify
both the namespace family and local name. Never accept a company extension or an
unrelated namespace solely because its local name or label is similar.

The namespace-family resolver must use explicit and tested namespace-URI rules. The
selected result must retain the exact stored namespace URI and display QName for
lineage.

### 6.3 Rule validation

Reject the rule set when:

- any metric key or display name is empty;
- the seven required metrics are not present exactly once;
- candidate ranks are duplicated or are not consecutive from zero;
- a candidate namespace family or local name is empty;
- a concept candidate is repeated within one metric;
- an instant metric is configured as duration or the reverse; or
- either version identifier is empty.

Tests must also verify that the packaged seven rules match the applicable entries in
mapping.txt.

## 7. Exact active snapshot selection

### 7.1 active_filing_snapshots

Add an active_filing_snapshots table:

    active_filing_snapshots
      filing_id       primary key
      snapshot_id     required
      published_at    required UTC timestamp

Enforce that snapshot_id belongs to filing_id through a composite foreign key to
evidence_snapshots(id, filing_id).

This table is a mutable pointer to current immutable evidence. Never infer the
current snapshot by selecting MAX(snapshot_id).

### 7.2 Publication changes

Extend EvidenceStore.publish_filing_window so the same transaction that publishes
active filing ranks also publishes each successful or reused filing's exact snapshot
ID. Remove bindings for filings leaving the active window.

The required snapshot IDs are already returned in per-filing ingestion outcomes.
Carry those IDs through CompanyIngestionService into publication rather than looking
them up again.

If a selected filing attempt fails and no usable snapshot is available, leave that
active filing without a binding. Mapping preflight must then refuse to publish a new
evaluation rather than turning missing evidence into seven missing mappings.

### 7.3 Migration backfill

Migration 0004 should backfill active filing bindings from the latest successful
processing_run_filings record with a non-null snapshot ID. If no unambiguous
successful snapshot exists, leave the binding absent and require an evidence refresh
before mapping.

## 8. Mapping preflight

For each requested company and report kind:

1. Load active exact-form filings ordered by active_window_rank.
2. Require five annual and twelve quarterly filings when a complete evaluation is
   requested.
3. Require one exact active snapshot binding for every selected filing.
4. Require one report-v1 evaluation of the matching report kind for every snapshot.
5. Verify snapshot artifacts when evaluation follows a local-reuse path.
6. Reject duplicate ranks, cross-company input, mixed form types, or incomplete
   bindings.

If preflight fails, return a mapping error and leave the last published metric
evaluation unchanged. Missing evidence is not a missing metric result.

## 9. Candidate population and eligibility

### 9.1 Separate report-kind unions

For annual and quarterly windows independently, derive:

1. Observed concept union: concepts referenced by actual stored fact occurrences in
   the selected snapshots.
2. Selectable concept union: concepts whose facts have evidence_role equal to
   selected_primary under the required report-v1 evaluations.

Do not build the observed union from every snapshot_concepts row. A concept used
only by a dimension or calculation relationship is not an observed Direct Mapping
fact.

Annual concept presence cannot establish quarterly coverage, and quarterly concept
presence cannot establish annual coverage.

### 9.2 Mapping-specific checks

After report-v1 selection, Direct Mapping must still verify:

- configured namespace family and exact local name;
- Target Metric period type matches the stored concept and context;
- context entity identifier matches the selected company after documented CIK
  normalization;
- the unit is a supported monetary unit;
- the context ends on the filing report date; and
- typed numeric text parses as a finite Decimal.

These checks protect the metric contract if report presentation rules change later.
Do not store a floating-point copy of the value. The selected fact already retains
exact typed and raw text, decimals, unit, period, context, and source location.

## 10. Resolution algorithm

Run one bounded batch for annual inputs and one for quarterly inputs:

    validate rule set
    load and validate active filing/snapshot/report-evaluation inputs
    derive observed and selectable concept unions
    fetch selectable facts matching any configured candidate
    group rows by snapshot, metric, and candidate rank

    for each metric:
        mapping_seen = any configured candidate in the report-kind observed union

        for each active snapshot:
            selected = first selectable candidate ordered by rank

            if selected exists:
                result = reported
                link exact selected fact
                retain candidate rank and resolution trace
            else if mapping_seen is false:
                result = missing / mapping_not_found
            else:
                result = missing / no_selectable_fact_for_period

Fallback rules:

- Rank zero is the primary concept.
- An alternative fills a period only when no higher-ranked candidate has a
  selectable fact for that period.
- A numeric zero is selectable and stops fallback.
- Never combine two candidates in one Direct Mapping result.
- Never sum dimensional members, average conflicts, or derive a missing value.
- Concept changes between filings remain visible through per-result fact links and
  candidate ranks.
- Six- or nine-month Operating Cash Flow facts cannot fill a discrete 10-Q period.
- No Q4 result is manufactured.

## 11. Result states and resolution traces

Use two top-level result states:

    reported
    missing

A reported result:

- has no missing reason;
- has a selected candidate rank;
- links exactly one fact; and
- may contain zero.

A missing result:

- has either mapping_not_found or no_selectable_fact_for_period;
- has no selected candidate rank; and
- links no fact.

Persist canonical resolution_trace_json for both states. It should contain:

- ordered candidate identities and ranks;
- whether each candidate was observed in the report-kind window;
- whether each candidate had a selected_primary fact for this snapshot;
- mapping-specific compatibility outcomes;
- existing report-v1 exclusion or conflict codes;
- selected candidate rank when reported; and
- source report evaluation ID.

Conflict and dimensional states remain visible in the trace. They should not become
top-level states because a conflicting primary candidate may still have a valid
configured alternative.

## 12. Persistence design

Create src/sec_inline_financials/storage/sql/0004_direct_mapping.sql.

### 12.1 target_metrics

Fields:

- id;
- metric_key;
- display_name;
- definition_version;
- expected_period_type;
- expected_unit_family; and
- created_at.

Use a unique key on metric_key and definition_version. Seed exactly the seven
target-metrics-v1 definitions deterministically.

### 12.2 metric_evaluations

Fields:

- id;
- company_id;
- report_kind: annual or quarterly;
- definition_version;
- mapping_rule_version;
- mapping_rule_hash;
- mapping_rule_json;
- source_report_rule_version;
- active_window_hash; and
- evaluated_at.

Calculate active_window_hash from canonical JSON containing, in rank order:

- form;
- active_window_rank;
- filing_id;
- snapshot_id;
- snapshot payload_hash; and
- report_evaluation_id.

Use a unique key covering company, report kind, definition version, mapping rule
hash, source report rule version, and active window hash. Reuse an exact match.

### 12.3 metric_results

Fields:

- id;
- evaluation_id;
- target_metric_id;
- snapshot_id;
- report_evaluation_id;
- status;
- missing_reason;
- selected_candidate_rank; and
- resolution_trace_json.

Use a unique key on evaluation_id, target_metric_id, and snapshot_id.

Database checks must enforce:

- reported has no missing reason and has a candidate rank;
- missing has an allowed missing reason and no candidate rank; and
- the report evaluation belongs to the same snapshot.

### 12.4 metric_result_facts

Fields:

- metric_result_id;
- snapshot_id;
- fact_id; and
- role, initially only selected.

Use composite foreign keys so a result cannot link a fact from another snapshot.
Allow one selected fact for Direct Mapping. A link table leaves room for later
approved composite mappings without weakening this milestone's invariant.

### 12.5 published_metric_evaluations

Fields:

- company_id;
- report_kind;
- evaluation_id; and
- published_at.

Use company_id and report_kind as the primary key. Enforce that the evaluation
belongs to the same company and report kind.

## 13. Atomic evaluation publication

Use the existing immutable-evaluation pattern:

1. Read and validate the active snapshot bindings.
2. Build the report-kind active-window hash.
3. Reuse an existing evaluation when all versions and hashes match.
4. Otherwise compute the complete result set outside the write transaction.
5. Start one short BEGIN IMMEDIATE transaction.
6. Re-read inputs and verify the active-window hash has not changed.
7. Insert the evaluation, all results, traces, and fact links.
8. Verify cardinality and fact-link invariants.
9. Update the published evaluation pointer.
10. Commit.

Any error before commit rolls back the new evaluation and leaves the prior published
evaluation intact. Mapping failure must not roll back a committed evidence ingestion
or active filing window.

A reader must compare the published evaluation's active-window hash with the current
active snapshot bindings. If they differ, expose the prior evaluation as stale rather
than presenting it as current.

## 14. EvidenceStore additions

Add focused methods rather than exposing SQL to callers:

    list_mapping_inputs(company_id, report_kind, report_rule_version)
    load_mapping_candidate_facts(snapshot_ids, concept_candidates)
    find_metric_evaluation(company_id, report_kind, versions, active_window_hash)
    save_and_publish_metric_evaluation(evaluation)
    get_published_metric_evaluation(company_id, report_kind)

The mapping interface should return detached typed records. Callers should not need
to know table names, transaction order, or join details.

## 15. Ingestion and refresh integration

Integrate mapping only after the standalone stored-evidence path is verified.

1. Publish exact active snapshot bindings with the evidence window.
2. After evidence publication succeeds, evaluate annual and quarterly mappings in a
   separate operation.
3. On reused_local, evaluate only when a published evaluation is absent or stale.
4. On checked_no_update, reuse an unchanged evaluation.
5. On updated, publish a new evaluation for each changed window.
6. On refresh_failed_using_local_data, keep the last published evidence and mapping
   evaluations.
7. If mapping fails after evidence publication, preserve the evidence window, keep
   the previous metric evaluation as stale, and return a separate mapping error.

Do not change the meaning of existing ingestion statuses. Mapping status should be
reported separately on CompanyIngestionResult.

Write mapping progress to stderr and keep existing ingestion summary lines on
stdout stable.

## 16. Stored-evidence command

Add a command such as:

    uv run --no-sync sec-inline-financials-map AAPL

The command should:

- initialize the existing evidence store;
- evaluate or reuse annual and quarterly mappings;
- print evaluation IDs and reported/missing counts;
- report incomplete inputs explicitly;
- avoid SEC_USER_AGENT requirements;
- construct neither an SEC gateway nor an Arelle processor; and
- create no TXT or complete-facts JSON report.

## 18. Required test matrix

Rule tests:

- Exactly seven Target Metrics exist.
- Candidate order is deterministic.
- Duplicate keys, ranks, or candidates fail.
- Missing rank zero fails.
- Rule serialization and hash are stable.
- Same local name from the wrong namespace does not match.

Resolver tests:

- Primary wins when primary and alternatives are selectable.
- The first available alternative fills only a period without a selectable primary.
- Zero remains reported and stops fallback.
- Annual and quarterly candidate populations are isolated.
- Instant and duration requirements are enforced.
- Entity and monetary-unit mismatches are rejected.
- mapping_not_found and no_selectable_fact_for_period are distinguished.
- Conflicting, dimensional-only, invalid, and excluded candidates remain visible in
  the trace.
- A conflicting primary may fall back to a valid configured alternative.
- Tag changes across periods preserve per-cell fact lineage.
- OCF six- and nine-month YTD values do not fill discrete quarters.
- No Q4 value is manufactured.

Storage tests:

- Migration 0004 applies once and records its checksum.
- Existing active filings backfill only unambiguous snapshot bindings.
- Cross-filing, cross-snapshot, and cross-company links fail.
- Reported and missing constraints reject invalid combinations.
- Reported results have exactly one selected fact.
- Missing results have no selected fact.
- Identical windows and rules reuse an evaluation.
- New windows or rules create a new evaluation without changing prior records.
- Mid-write failure leaves no partial evaluation or publication pointer.

Integration tests:

- One bounded candidate load occurs per report kind, not per metric-period cell.
- Complete 5/12 evidence produces 119 results.
- Incomplete evidence publishes no new evaluation.
- reused_local creates a missing evaluation when needed and otherwise reuses it.
- checked_no_update does not duplicate evaluations.
- updated publishes an evaluation for the new evidence window.
- Mapping failure preserves evidence and the prior published evaluation.
- The mapping command creates no SEC client, Arelle processor, TXT report, or JSON
  report.

## 19. Performance constraints

The active window is small. Prefer complete, bounded recomputation over mutable
per-cell updates.

- Resolve configured concept identities once per rule set.
- Execute one candidate-fact query per report kind.
- Reuse current active-window, fact-concept, context-period, and report-role indexes.
- Add indexes for active snapshot lookup, evaluation reuse, metric-result grid
  lookup, and fact-link traversal.
- Group only candidate facts for the seven metrics in Python.
- Insert a complete evaluation in one transaction.
- Never load every stored fact into Python for each metric.
- Never parse report text or exported JSON.
- Never convert exact numeric values to float.

## 22. Definition of done

Direct Mapping is complete when:

- the runtime rule set contains exactly the seven Target Metrics and has stable
  version and hash identities;
- every usable active filing points to one exact immutable snapshot;
- annual and quarterly candidate populations are independently derived;
- all seven metrics are evaluated for every selected filing period;
- a complete 5/12 window contains exactly 119 results;
- every reported result links exactly one stored fact and preserves zero;
- every missing result records a high-level reason and detailed trace;
- repeated identical evaluation is idempotent;
- new windows or rule versions create new immutable evaluations;
- failures never replace the previous published evaluation or roll back stored
  evidence;
- no Direct Mapping path contacts the SEC, opens Arelle, calls an LLM, or generates
  a report;
- automated ingestion, storage, retrieval, resolver, service, and integration tests
  pass;
- Ruff, formatting, strict mypy, and build checks pass; and
- stored-evidence AAPL acceptance is recorded with exact scope and limitations.

## 23. Acceptance record

Acceptance ran on 2026-09-15 against the existing local AAPL evidence-v2 store.
It used the published five-annual/twelve-quarter window and persisted report-v1
evaluations. It did not contact the SEC, open Arelle, call an LLM, or generate a
TXT/JSON report.

First run:

    AAPL: direct mapping complete
    Annual evaluation 1: 35 reported, 0 missing (created)
    Quarterly evaluation 2: 76 reported, 8 missing (created)

All eight quarterly missing results were Operating Cash Flow with
no_selectable_fact_for_period. The stored report-v1 evidence did not contain an
eligible discrete-quarter selected fact for those periods; Direct Mapping did not
substitute six- or nine-month year-to-date facts.

The second identical run reused annual evaluation 1 and quarterly evaluation 2.
The deterministic synthetic acceptance produced all 119 reported results for a
