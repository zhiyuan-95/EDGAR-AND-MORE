## Problem Statement

The shipped lineage-maintenance command can extend a stored company lineage only backward. Given a stored successor CIK and a new predecessor CIK, it previews and commits `predecessor -> successor`, keeps the existing canonical CIK, and then runs the existing full-lineage ingestion process.

It cannot represent the opposite boundary change: a stored canonical company receives a distinct new successor CIK. For an existing lineage `B -> A`, the operator needs to add `A -> N`, make `N` the canonical current CIK and current legal name, preserve `A` and `B` as historical registrants, and then ingest through the resulting `N -> A -> B` current-to-oldest lineage.

This is a focused amendment to the approved lineage design. It is not automatic successor discovery, a new ingestion architecture, or a general legal-entity transition system.

## What Makes This Cool

Predecessor extension and successor promotion become two directions of the same trusted operator instrument. The preview, approval boundary, commit-before-ingestion sequence, retry behavior, and output remain familiar; only the lineage mutation changes. A high-impact canonical-identity change therefore feels no more mysterious than the lineage maintenance already shipped.

## Constraints

- Preserve the existing stages exactly: preview, `[y/n]` approval, lineage commit, existing ingestion, existing result and retry reporting.
- Preserve the existing approval shape: canonical company, existing lineage, proposed direct edge, optional effective date, and new/already-present status. Do not add an SEC-evidence block.
- Use this successor-specific prompt: `Create this lineage and ingest the successor's filings? [y/n]:`.
- Only `y` or `Y` approves. `n`, blank input, or EOF cancels without mutation; invalid input repeats; Ctrl-C retains the current exit behavior.
- Commit the approved lineage promotion before invoking ingestion, exactly as predecessor maintenance commits its edge first. If ingestion fails or finds no eligible filings, retain the promotion and instruct the operator to rerun safely.
- Preserve the existing `companies.id` and ticker. Within the existing `companies` row, change only `cik`, `current_name`, and `updated_at`; the required `company_ciks` membership and `company_cik_transitions` inserts remain allowed.
- Preserve every existing filing's immutable identity and source metadata, its registrant CIK and archive-owner CIK, all evidence artifacts, and all `filing_provenance` values. The successor-promotion transaction itself must not rewrite filing data. The existing ingestion/publication stage may update only its normal active-window publication state, including `filings.is_active`, `filings.active_window_rank`, `active_filing_snapshots`, and refresh dates.
- Retain the graph invariant: one connected, acyclic, unbranched predecessor-to-successor chain whose sink is the canonical current CIK. This amendment does not introduce cross-edge effective-date ordering: dated and undated adjacent edges remain accepted exactly as they are today, while a verified date on the same exact edge remains immutable.
- Limit this amendment to distinct-CIK promotion. Same-CIK legal succession and automatic legal-evidence discovery are outside scope.
- Do not change ordinary ticker ingestion into an interactive workflow. Successor promotion remains an explicit operator command.
- Do not edit applied migrations. The current schema already supports an additional member, a direct transition edge, and a canonical CIK update, so no migration is expected.

## Premises

- For an initial promotion, the operator supplies the exact stored current CIK as the predecessor, the exact new successor CIK, and an optional verified effective date. On a rerun, the operator repeats the same arguments even though that predecessor CIK is now historical and the successor is current. Operator verification and explicit approval remain the authorization boundary, matching existing maintenance.
- On a new promotion, the supplied predecessor CIK must be the current canonical sink. The new successor CIK must not belong to another stored company.
- On a rerun, the supplied predecessor is now historical: the exact `predecessor -> successor` edge may already exist and the successor may already be canonical. That state is valid and must lead to idempotent re-ingestion rather than a duplicate edge.
- SEC registrant resolution is used for normalized CIK identity and current legal names, as in predecessor maintenance. A ticker/CIK mismatch alone is not proof of succession.
- After the lineage transaction commits, `CompanyIngestionService.ingest_company_cik(new_successor_cik)` can use the existing membership and canonical-company lookup to discover and ingest the complete current-to-oldest lineage.

## Cross-Model Perspective

The cold Codex review proposed a durable “promotion capsule” that would prepare filings and publish the filings, edge, and canonical change in one transaction. It correctly emphasized stale-preview protection, idempotency, and all-old-or-all-new state, but it changed the shipped maintenance stages. The user rejected that premise: successor maintenance must retain the existing commit-before-ingestion behavior, so this amendment keeps the current state-hash check and retry semantics without adding staging, Temporal, an operation journal, or a second ingestion path.

## Approaches Considered

### Approach A: Companion successor operation — selected

Add a narrow successor-specific preview and store mutation beside the existing predecessor operation, while sharing only the CLI helpers needed to keep preview, confirmation, result, and retry behavior identical. This is the smallest change that matches the requested behavior.

### Approach B: Direction-aware maintenance engine — rejected

Generalizing both directions behind a new operation type would reduce future drift but unnecessarily refactor the already-working predecessor path.

### Approach C: Desired-chain diff — rejected

Diffing an arbitrary desired chain would enable broader reconciliation and repair behavior beyond this single boundary append.

## Recommended Approach

### 1. Add a companion successor preview

In `src/sec_inline_financials/company_lineage.py`, add `LineageMaintenanceService.preview_successor_promotion(predecessor_cik, successor_cik, *, effective_date=None)`. The predecessor must be canonical for a new promotion; it may be historical only when the exact approved edge already exists on an idempotent rerun.

Reuse `LineagePatchPlan`; it already carries the company, predecessor identity, successor identity, before/after lineages, expected state hash, and idempotency status. For this operation:

- `plan.predecessor` is the stored old canonical CIK `A`.
- `plan.successor` is the new current CIK `N`.
- `plan.before` is the currently stored lineage.
- `plan.after` is the approved lineage with canonical `N` and current-to-oldest members `(N, A, B, ...)`.

For a new promotion, the preview must:

1. Normalize both CIKs and reject equality.
2. Load the company lineage through the supplied old canonical CIK.
3. Require the supplied old CIK to equal `before.canonical_current_cik`.
4. Resolve both registrant identities through the existing resolver.
5. Reject a new successor already owned by another company or attached elsewhere in the same lineage.
6. Construct the direct `A -> N` edge with the optional effective date.
7. Construct and validate `after` with `N` as the canonical sink, `N` prepended to `current_to_oldest`, and the new edge appended.

For an idempotent rerun, the preview must accept an existing exact `A -> N` edge when `N` is already canonical. Preview is read-only: it may propose refreshed legal names and a previously missing effective date in the plan, but only the apply transaction writes them. It must reject a conflicting previously verified date. Any other placement of `A` or `N` is an error rather than an implicit repair.

The preview records the existing `before.state_hash`. Its current deterministic inputs are the canonical CIK, ordered member CIKs, direct edges, and each edge's optional effective date. Legal names, `associated_at`, `updated_at`, and other generated values remain excluded, matching the shipped predecessor workflow. The store must recheck the hash inside the write transaction so approval cannot be applied after a topology, canonical-CIK, membership, or effective-date change; concurrent legal-name refreshes retain the existing last-approved-name behavior.

### 2. Add one successor-specific lineage transaction

Extend the `LineageStore` protocol and `EvidenceStore` with `apply_successor_promotion(plan)`; do not alter `apply_lineage_patch()` semantics.

Inside one existing `write_transaction()`:

1. Reload the lineage through `plan.predecessor.cik` and verify `company_id` and `expected_state_hash`.
2. Locate the exact approved `predecessor -> successor` edge in `plan.after`.
3. For a new promotion, recheck that the predecessor is still canonical and that the successor has no owner.
4. Refresh the predecessor member's legal name.
5. Insert the successor into `company_ciks` under the same `company_id`.
6. Insert the direct transition into `company_cik_transitions`.
7. Update the existing `companies` row to `cik = successor`, `current_name = successor.legal_name`, and a new `updated_at`; do not change its `id` or ticker.
8. Reload through the successor CIK and require its state hash to equal `plan.after.state_hash` before commit.

For an already-present exact promotion, refresh `company_ciks.legal_name` for both the predecessor `A` and successor `N`, and refresh `companies.current_name` for canonical `N`. Apply an allowed missing effective date through the existing idempotent pattern, verify the successor remains canonical, validate the resulting state hash, and return `updated` or `already_present` without inserting duplicate membership or transition rows. Preview edge status and apply result are separate values: preview shows `new edge` or `already present`; final reporting shows `created` for a newly inserted edge, `updated` when a missing effective date is filled, or `already_present` when no edge/date change was required. A legal-name-only refresh retains the existing `already_present` result semantics and leaves the topology hash unchanged because names are intentionally excluded.

The transaction must not update or recreate historical filings, snapshots, sections, mappings, artifacts, or filing-provenance rows.

### 3. Reuse the existing apply-then-ingest sequence

Add `LineageMaintenanceService.apply_successor_and_ingest(plan)` as the companion to `apply_and_ingest(plan)`:

1. Require the ingestion callback before mutating, matching the current guard.
2. Call `apply_successor_promotion(plan)`.
3. Call the same ingestion callback with `plan.after.canonical_current_cik`, which is `N` on both the initial promotion and every rerun.
4. Return the existing `LineageMaintenanceResult`.

There is deliberately no rollback across the lineage and ingestion stages. Once approved, a successful lineage transaction remains authoritative even if SEC discovery, downloading, Arelle processing, or filing selection later fails. The same command reruns against the already-present edge and retries ingestion idempotently.

### 4. Add an explicit companion CLI entry point

Add this console script without changing the positional meaning of the existing predecessor command:

```text
sec-inline-financials-lineage-change <PREDECESSOR_CIK> <SUCCESSOR_CIK> [--effective-date YYYY-MM-DD]
```

Point the script at a successor-specific `promotion_main()` in `lineage_cli.py`. It must initialize the same store, request the same schema-upgrade approval when needed, create the same SEC client and ingestion service, and invoke the new successor preview and apply methods.

Keep the predecessor and successor preview/mutation methods direction-specific, but narrowly extract their shared CLI workflow. Both command runners must pass a materialized `LineagePatchPlan`, direction-specific prompt, apply-and-ingest callback, and exact rerun command into one internal helper that owns `_render_plan`, the `[y/n]` confirmation loop, cancellation and interruption behavior, apply/ingest exception handling, exit codes, result rendering, and retry guidance. Do not introduce a generic lineage-operation framework. The visible preview remains:

```text
Canonical company
  <stored current name> (current CIK <A>)

Existing lineage
  <A>  <name>
  <B>  <name>

Proposed direct edge
  <A>  <old canonical name>
       ->
  <N>  <new successor name>
  <A> -> <N>
  Effective date: <date>      # only when supplied or already stored
  Status: new edge            # or already present
Create this lineage and ingest the successor's filings? [y/n]:
```

When rendering existing members, use the resolved name for either endpoint if that endpoint is already present. This retains the same layout while making the renderer correct in both directions.

Cancellation must continue to say that no lineage or ingestion changes were made. Post-approval failures must continue to say the lineage may already be committed and show the exact successor-promotion rerun command. `checked_no_filings` remains a nonzero result with the lineage retained.

On an already-present rerun, the same renderer shows `N` in the “Canonical company” section and lists the existing lineage as `N, A, B, ...`; the proposed direct edge remains `A -> N` with `Status: already present`. The positional arguments remain `A N`, even though `A` is now historical.

### 5. Keep automatic ticker ingestion unchanged

Do not make `CompanyIngestionService.ingest_company(ticker)` prompt or auto-promote when SEC resolves the ticker to a different CIK. Its current mismatch error remains a signal for the operator to verify the transition and run the explicit promotion command. After promotion, the preserved ticker points to the updated canonical CIK, so ordinary ingestion can continue normally.

### 6. Verification plan

Add focused tests without weakening existing predecessor coverage.

Domain and service tests:

- `B -> A` previews as `B -> A -> N`, with canonical `N` and current-to-oldest `(N, A, B)`.
- A noncanonical predecessor, same CIK, cross-company successor, attached same-company successor, and conflicting effective date are rejected.
- Adjacent dated or undated edges retain current behavior; this amendment adds no monotonic effective-date rejection rule.
- A rerun recognizes the exact existing edge and produces no duplicate member or transition.
- A legal-name-only rerun refreshes both `company_ciks` endpoint names and canonical `companies.current_name`, returns `already_present`, and leaves the topology state hash unchanged.
- A missing ingestion callback prevents mutation.
- The ingestion callback runs after the transaction, receives `N`, and can observe `N` as canonical.
- An ingestion exception leaves `N` canonical and the `A -> N` edge stored.

Store tests:

- `companies.id` and ticker remain unchanged while `companies.cik/current_name` become the successor values.
- Old members remain in `company_ciks`; the new successor is added once.
- The lineage-promotion transaction leaves existing filing and provenance rows byte-for-byte unchanged.
- A full first-run promotion followed by successful ingestion preserves every preexisting accession and its immutable filing/source fields, registrant CIK, archive-owner CIK, evidence artifacts, and `filing_provenance` values, while allowing newly ingested successor filing/provenance rows to use the successor CIK. The test permits the existing publication path to update active flags, active-window ranks, active-snapshot bindings, and refresh dates.
- A stale preview is rejected before any mutation.
- Transaction fault injection leaves either the complete old lineage or the complete promoted lineage.
- `PRAGMA foreign_key_check` and lineage reconstruction succeed after promotion.

CLI tests:

- The preview shape and successor prompt match the approved text exactly.
- `y` and `Y` approve; `n`, blank, EOF, invalid input, and Ctrl-C retain existing behavior.
- Cancellation performs neither lineage mutation nor ingestion.
- Success, `checked_no_filings`, ingestion error, and interruption retain the current exit and retry semantics.
- The rerun message uses `sec-inline-financials-lineage-change A N` and preserves `--effective-date` when present.
- Existing predecessor CLI and migration-approval tests remain unchanged and passing.
- **CRITICAL regression coverage:** because the shared CLI helper refactors the shipped predecessor path, retain predecessor-specific assertions for its exact prompt, argument order, apply callback, rerun command, cancellation, success, `checked_no_filings`, ingestion error, and interruption behavior. Parameterize only genuinely identical helper behavior; keep direction-specific assertions explicit so swapping `A B` and `A N` cannot pass accidentally.
- Preserve the existing pre-approval identity-failure behavior without adding a new error path. For both predecessor maintenance and successor promotion, cover a resolver response with the wrong CIK, a blank legal name, and a resolver `DiscoveryError` such as a network failure; assert exit code `1`, a clear `Error: ...` message, no lineage confirmation prompt, and no lineage or ingestion mutation. A separately approved schema migration may already have committed before identity resolution, matching the existing command order.
- Exercise the actual `sec_inline_financials.lineage_cli:promotion_main` console target in isolated subprocess tests. For a pending schema, declining approval leaves the database byte-for-byte unchanged, while approval completes migration before successor-lineage validation. A current schema skips the migration prompt, and an unsupported newer schema is rejected without mutation.

Integration coverage:

- After promotion, `ingest_company_cik(N)` discovers the full `N, A, B` registrant set and rebuilds the active annual and quarterly window through the existing rules.
- Repeating the approved command is idempotent for lineage, filings, snapshots, and provenance.

Run the established repository gates for the touched Python surface: focused lineage and CLI tests first, then the full pytest, Ruff check/format check, and mypy suite.

## Success Criteria

- Starting from `B -> A`, approving `A -> N` produces one connected `B -> A -> N` chain with `N` canonical.
- The operator sees the same preview sections and `[y/n]` interaction used by existing maintenance, with only successor-specific ingestion wording.
- Cancelling makes no changes.
- After approval, ingestion uses the existing full-lineage path and starts from `N`.
- An ingestion failure retains the promoted lineage and gives an exact safe rerun command.
- `companies.id`, ticker, and all historical filing provenance remain unchanged.
- A rerun creates no duplicate membership, transition, filing, snapshot, or provenance rows.
- No new database migration, staging store, workflow journal, or alternate ingestion path is introduced.

## Engineering Review Addendum

### NOT in scope

- Automatic successor discovery from SEC filings — operator verification remains the authorization boundary.
- Same-CIK legal succession — this amendment covers only a distinct new CIK.
- A generic direction-aware lineage engine or desired-chain reconciler — the selected design adds one narrow companion operation.
- Atomic publication of lineage and filing ingestion — the shipped commit-before-ingestion and safe-rerun semantics remain unchanged.
- A new database migration, staging store, workflow journal, or alternate ingestion pipeline — the current schema and ingestion path are sufficient.
- An SEC-evidence block in the approval preview — the preview remains identical in shape to existing maintenance.
- Automatic prompting from ordinary ticker ingestion — a ticker/CIK mismatch remains an operator signal, not proof of succession.
- A new monotonic ordering rule across transition effective dates — existing dated and undated adjacency behavior remains unchanged.
- A web UI or service endpoint — this is an explicit local operator command.

### What already exists

- `LineageMaintenanceService.preview_link()` already normalizes CIKs, validates the stored chain, resolves SEC registrant identities, and produces `LineagePatchPlan`; the successor preview reuses those types and validation conventions rather than rebuilding them.
- `LineagePatchPlan.expected_state_hash` and `EvidenceStore.write_transaction()` already provide stale-preview rejection and atomic lineage writes; the successor transaction applies the same pattern.
- `EvidenceStore` already stores globally unique lineage members, direct transitions, and a mutable canonical CIK on a stable company row; no schema redesign is needed.
- `LineageMaintenanceService.apply_and_ingest()` already establishes commit-before-ingestion behavior and retained lineage after ingestion failure; the successor companion preserves that sequence and changes only the CIK passed to ingestion.
- `run_lineage_command()` already owns the preview, `[y/n]` loop, exit codes, result rendering, and retry guidance; a narrow shared helper preserves this behavior for both commands.
- `ensure_schema_upgrade_approved()` already provides the separate migration-approval boundary; `promotion_main()` must call it in the same position.
- `CompanyIngestionService.ingest_company_cik()` already loads the complete stored lineage and publishes the annual and quarterly active windows; no successor-specific ingestion path is added.
